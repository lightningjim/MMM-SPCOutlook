<objective>
Close `18-VERIFICATION.md` gap 3 (CR-01). `node_helper.js:4755-4761` documents the contract in the
file's own words: a rejected `Promise.allSettled` member substitutes `payload: null`, and every
downstream consumer guards on a falsy/non-object block before reading into it, so one product's
failure degrades silently rather than throwing. Phase 18 added three reads that violate it with no
guard:

1. `node_helper.js:4887` — `JSON.stringify(eroPayload.day1ValidTime)`, unguarded.
2. `node_helper.js:5013-5017` — both `_addRegistryDayGridEntries` call sites; the function's only
   early return is the toggle gate, which does NOT fire for a product that is enabled but whose
   runner rejected, so the day loop reaches `payload[\`day${d}Risk\`]` on `null`.
3. `node_helper.js:5035` — `_buildGridSummary(gridDays, hazardsPayload.windowBand, ...)`; the
   property read happens at the call site, before `_buildGridSummary`'s own `Array.isArray` guard
   ever runs.

Any one of the six settled members rejecting therefore throws a `TypeError` that escapes to
`getSpcOutlook`'s outer catch, which returns `{ error }`, and `MMM-SPCOutlook.js:421-422` renders
`wrapper.textContent = "Error: " + this.spcrisk.error`. The entire display goes blank — including
SPC convective and HeatRisk data that fetched cleanly in the same poll.

Purpose: this is the identical "total outage rendering as a confident all-clear" shape 14-REVIEW's
round-3 deep review found as that phase's highest-severity finding, and the comment quoted above was
written specifically to prevent it. Phase 19's plan explicitly assumes "the payload Phase 18 already
validated", with no legacy fallback, so this must not carry forward. None of the existing scenarios
reaches the `allSettled` rejection branch, so the regression is invisible to the phase's own suite.

Output: three guards, one scenario that forces genuine runner rejections and proves the rest of the
payload survives, and a `deferred-items.md` entry recording the half of WR-01 this plan deliberately
does not close.
</objective>

<decision>
## One guard at the head of the function, not two at the call sites

`_addRegistryDayGridEntries` gets `if (!payload || typeof payload !== "object") return;` as its
FIRST statement, before the existing toggle gate. Both call sites are then covered by one check.
Two call-site guards would be the WR-06 divergence shape this file already argues against — a fix
applied to one twin and not the other.

The other two sites are guarded expressions at the read: `eroPayload && eroPayload.day1ValidTime`
and `hazardsPayload && hazardsPayload.windowBand`. `_buildGridSummary`'s internal
`Array.isArray(windowBand)` guard already handles the resulting `null`/`undefined` correctly, so
nothing inside that function changes.

## `assertPayloadIntact(out)` is NOT the right oracle for a run with a rejected member — read this before writing the scenario

`18-VERIFICATION.md`'s `missing:` entry says the new scenario should assert
"`assertPayloadIntact(out)` still holds". Verified against the shipped oracle
(`scripts/probe-payload-resilience.js:1021` onward): it dispatches over every `PRODUCT_REGISTRY` row
and requires each product's payload block to be a non-null object. `getSpcOutlook`'s return sets
`excessiveRain: eroPayload`, `hazardsOutlook: hazardsPayload` and so on directly, so a genuinely
rejected member makes that block `null` BY DESIGN — that is the documented degrade, not a
regression. Calling `assertPayloadIntact` wholesale on such a run would therefore fail even after a
perfect fix.

Do NOT weaken, parameterise or fork `assertPayloadIntact` to make it pass — roughly sixty scenarios
depend on it as the D-05 payload-shape oracle, and loosening it to accommodate one scenario would
retire coverage far wider than this gap.

The contract CR-01 actually names is narrower and is asserted directly instead:
`out.error === undefined` (no total collapse), the REJECTED product's block is exactly `null` (the
documented degrade, and the proof the rejection really happened), and every OTHER product's block
still passes its own targeted intactness helper with its real fetched values intact.
`assertPayloadIntact` is then applied in full to a third, no-rejection control run, which proves the
fixture is otherwise healthy and that the nulls in the first two runs are attributable to the forced
rejection rather than to a broken fixture.

## Review-warning rider WR-01: half closed here, half deliberately left open

WR-01 records that `sources[].reportedDays` is derived from a seeded default rather than a real
fetch-success signal, so a fetch FAILURE reads as "the source answered no risk" for four of the six
day-scoped sources. The head guard this plan adds closes the REJECTION half of that for `wpc-ero`
and `wpc-wssi`: a rejected runner now reports no days at all.

The remaining half — `_runArcGisDayProduct` seeds every `day{N}Risk` to `"NONE"` before its own
fetch gate, so a hard fetch failure still leaves a string tier that `_addRegistryDayGridEntries`
reads as an answer — is NOT closed here and must not be. Its fix threads an `answeredDays`
side-channel out of `_runArcGisDayProduct` and an `answered` flag through the SPC inline chain into
`_addSpcGridEntries`: three functions, two products and a runner signature change, none of which any
gap's `missing:` list requires and none of which this plan is otherwise touching. It is recorded in
`deferred-items.md` in Task 3 so it is carried rather than lost.
</decision>
