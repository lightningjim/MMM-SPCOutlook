<decision>
## LOCKED DECISION D-21: the Hazards Outlook `end_date` endpoint is read INCLUSIVELY on the day-grid path

`const lastGridDay = gridEnd;` — wholesale, with no `start_date === end_date` special case and no
per-group branch.

This SUPERSEDES the 18-10 decision recorded in `.planning/STATE.md`
("`Math.max(gridStart, gridEnd - 1)` ... to tolerate both conventions"). That expression tolerates
both conventions only for a span confined to a single grid day; for every longer span it silently
resolves to the exclusive reading, which is the defect.

**The tension, stated honestly.** The upstream feed is not internally consistent.
`18-LIVE-CAPTURE.md`'s Criterion 1 section records both forms live in the same 2026-09-05 poll: a
Precipitation feature with `start_date === end_date` (inclusive / zero-duration) and a Temperature
feature with `end_date = start_date + 86400000` (exclusive). Reading inclusively always gives a
genuinely exclusive multi-day span one spurious trailing day; reading exclusively always loses the
last day of a genuinely inclusive span, which is the present defect.

**Why inclusive wins, on four independent grounds:**

1. **Only the Precipitation group reaches this grid, and Precipitation was the group observed using
   the inclusive form.** `_addHazardsOutlookGridEntries` routes every non-`precipitation` group to
   the window band unconditionally (`match.group !== "precipitation"` -> `continue`, node_helper.js
   ~2859). The exclusive-form Temperature feature the live capture recorded therefore never reaches
   this code path at all. The one live sample of the group that DOES reach it was inclusive.
2. **Parity with the legacy block, which is D-01's whole point.** `_bucketHazardMatch`'s day loop is
   `for (let d = Math.max(offsetStart, firstDay); d <= Math.min(offsetEnd, lastDay); d++)` — both
   endpoints inclusive. D-01 permits two representations of the same data to coexist for one phase
   only on the premise that they are built from the same in-memory values; two different endpoint
   conventions over those same values is exactly the drift D-01 was written to bound. Inclusive
   makes the two agree by construction rather than by coincidence.
3. **The project's no-false-negative rule breaks the tie.** Over-reporting one day is a cosmetic
   cost on a broad-brush Day 3–14 product; under-reporting one day is a hazard that fails to
   display, which PROJECT.md names as the most severe defect class here.
4. **`18-VERIFICATION.md`'s own `missing:` entry asks for exactly this** — "Read the Hazards
   Outlook end_date endpoint inclusively for multi-day spans ... matching `_bucketHazardMatch`'s own
   inclusive loop, so `days[]` and the legacy block agree."

**Bound safety is unchanged and non-negotiable.** The clamp stays at the loop HEADER
(`clampedStart = Math.max(gridStart, 1)`, `clampedEnd = Math.min(lastGridDay, GRID_DAY_COUNT)`),
never in the body. A hostile or absurd `end_date` still yields at most fourteen iterations
(T-18-03 / T-16-05, an existing locked constraint). Widening `lastGridDay` from `gridEnd - 1` to
`gridEnd` does not touch that clamp.
