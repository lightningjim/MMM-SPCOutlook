<objective>
Close CR-01: make a hostile ERO response degrade that one day to no-risk instead of destroying the entire outlook payload.

Purpose: Phase 14's verification scored 9/10 with one blocking gap. ArcGIS REST returns invalid-layer, service-restart, throttling, and token errors as HTTP 200 with a body carrying `error` and no `features`. `fetchGeoJsonCached` validates only HTTP status, `extractPolygons` unconditionally dereferences `geojson.features.forEach`, and nothing catches the resulting TypeError before `getSpcOutlook`'s function-wide catch replaces the whole payload with `{ error }`. A default-off optional product can therefore take the module's primary SPC display offline whenever a third-party host hiccups. This directly violates D-05 ("a product toggle being off/on never changes the payload shape") and, because the flaw sits in shared helper code and in the loop Phases 15-17 copy verbatim for WSSI, MPD, Hazards Outlook, and HeatRisk, it would be inherited four more times.

Output: `node_helper.js` with a hardened `extractPolygons`, a reusable `_isFeatureCollection` predicate, and a per-day guarded ERO loop — verified by plan 14-06's probe going from `3 passed, 3 failed` to `6 passed, 0 failed`.

DATA-01 appears in this plan's `requirements` as a **regression guard, not new work**: it was satisfied by plan 14-01 and verification marks it SATISFIED. A hotfix on a fetch path is exactly where a fallback URL or an `f=` literal would plausibly be introduced, so Task 2 carries an explicit criterion that `node_helper.js` still contains no NOAA host and no format literal.
</objective>

<design_rationale>
Read this before Task 1. It records the choice the gap analysis explicitly asked to be justified in the plan.

**Why the fix is NOT in `fetchGeoJsonCached`.** Putting shape validation inside the fetch helper is the tempting single-point fix: 20 call sites would inherit it with no edits. It is rejected for three reasons.
1. **Contract blast radius.** Every one of those 20 call sites is written against the helper's four return shapes and branches on `data === null && cachedResult !== null`. Changing what the helper may return puts all of SPC and fire weather in the diff of a gap-closure hotfix, which is exactly the risk concentration D-08 was written to avoid.
2. **It is not verifiable in this project.** `fetchGeoJsonCached` closes over a module-scope lazy `import('node-fetch')`. A probe cannot substitute that without editing source, so a change there could only be accepted on static reading — a downgrade in rigor versus the runnable acceptance this plan uses everywhere else.
3. **It is unnecessary.** The per-day try/catch in Task 2 contains *everything* the helper can do wrong, including its genuinely unguarded `JSON.parse` throwing a SyntaxError on an HTML error page. Containment at the consumer subsumes validation at the producer.

**Where reusability actually lands.** The gap analysis required the fix to sit where the next registry row inherits it for free rather than being pasted per-product. Two places satisfy that without touching the fetch contract:
- `extractPolygons` is called by *every* product — SPC categorical, SPC probability, CIG, fire weather, ERO, and every Phase 15-17 row. Hardening it there is one edit that protects all of them.
- `_isFeatureCollection` is a named, greppable one-liner method living beside `extractPolygons`. A Phase 15-17 product row copies one `if` line, not a hand-rolled guard, and a reviewer can count call sites against registry rows.

**Why a rejected body must not be cached.** `_geoJsonCache.set` on a bad response would store `mode` and `etag` alongside a garbage result. On the next poll `fetchGeoJsonCached` sends `If-None-Match`, the server answers 304, and the cache-hit branch returns the garbage indefinitely — the WR-08 shape, permanently pinned. Skipping the cache write on rejection is therefore load-bearing, not tidiness.

**Why a failed day is not marked stale.** D-04 states ERO fetch results roll into the existing global `anyStale` flag "exactly like SPC layers", and per-product staleness UX is explicitly out of scope this phase. SPC layers set `anyStale` only from `fetchResult.stale`. Inventing a new `anyStale` trigger for a rejected ERO body would make ERO behave unlike every SPC layer and would put a `_stale` banner on a payload whose SPC data is perfectly fresh. The ERO path keeps the existing `if (fetchResult.stale) anyStale = true;` line unchanged — which still fires when the helper serves a stale fallback — and makes a rejection observable through `Log.error` instead. Record this reasoning in the code comment so a later reader does not "fix" it.
</design_rationale>
