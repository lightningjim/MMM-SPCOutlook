Add the `showExcessiveRain` user config flag, send it to the backend in the nested `products` object, render ERO rows for Days 1-5, and extend the combinatorial no-risk gate so an ERO-only risk is not suppressed.

If ERO ships without extending that `&&`-chain, a location with an active ERO risk and nothing else renders the no-risk message and every ERO row is suppressed behind it.

CONTEXT.md's D-06 also says "each new product flag defaulting to `false`" — the `true` in D-06's parenthetical is an example of a *user's* config value, not the default. The default is `false`.

- **Only `showExcessiveRain` is added to `defaults:` this phase — not six speculative flags.** CONTEXT.md's Integration Points note mentions "the six `show*` booleans", but shipping five documented toggles for products that do not exist yet means five user-facing switches that silently do nothing. CFG-01 is satisfied per-product as each product lands; Phases 15-17 add their own flag next to their own product. Nothing about the `products` wire object, the registry, or the payload shape needs to change to accept them later.

The per-day NONE check alone would already suppress rows when the backend is disabled, but the explicit config gate makes the intent legible and keeps the no-risk gate honest if a future payload arrives from a differently-configured backend.

Scope boundaries: do **not** restructure `getDom()` — that is Phase 19's single-purpose rewrite (RPT-01..06) and is the milestone's highest-risk work. Do not add proximity badges to ERO rows (deferred to MERGEX-01). ## Trust Boundaries

Single-user local MagicMirror display appliance. No authentication, session, access-control, or multi-tenant surface exists in this module and none is invented below.

| Boundary | Description |
|----------|-------------|
| User config (`config.js`) -> frontend module | The user's own file, edited by the user, on their own machine — trusted input, not an attacker-controlled channel |
| Frontend -> node_helper (socket) | The `products` object crosses a local process-to-process notification channel |
| `this.spcrisk` payload -> `wrapper.innerHTML` | External NOAA-derived strings are concatenated into HTML in `getDom()` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-03 | Tampering | `showExcessiveRain` config value of an unexpected type | mitigate (backend) | The frontend passes the config value through as-is; the authoritative coercion is `products?.showExcessiveRain === true` in `node_helper.js` (plan 14-03), which cannot be bypassed because it is the only thing the ERO fetch gate reads. Frontend-side, a non-boolean value can at most affect this user's own render on this user's own machine. |
| T-14-08 | Tampering | NOAA-derived tier strings interpolated into `wrapper.innerHTML` | mitigate (by construction) | The ERO render block interpolates only `dayNText` and `dayNColor`, and neither is a raw upstream string: both are looked up backend-side through the registry's fixed `tierToText` / `tierToColor` maps keyed on a tier value from the closed set `{NONE, MRGL, SLGT, MDT, HIGH}`. An unmapped `dn` value degrades to `NONE` via the `|| 0` fallback rather than passing an attacker-influenced string through. No raw `properties.outlook`, `properties.snippet`, or `valid_time` string is ever rendered — `valid_time` is carried in the payload but deliberately not displayed (D-03). This means no NOAA response content reaches `innerHTML` verbatim. |
| T-14-09 | Denial of Service | Malformed payload (missing `excessiveRain` key) throwing inside `getDom()` and blanking the module | mitigate | Both the render block and the no-risk gate guard on `this.spcrisk.excessiveRain` existence before dereferencing any `dayN` field, mirroring the existing `if (this.spcrisk.fireWeather)` precedent. A payload from an older backend renders the pre-phase display rather than throwing. |
| T-14-SC | Tampering | npm / package-manager installs | accept (not applicable) | Zero new packages this phase; RESEARCH.md's Package Legitimacy Audit confirms no install step and no legitimacy gate is required. |
