<planner_resolutions>
Both remaining "Claude's Discretion" items from CONTEXT.md are resolved here, plus RESEARCH.md's open naming question. Implement as stated.

- **Where toggle defaults are applied: BOTH ends.** The frontend `defaults:` block declares `showExcessiveRain: false` (plan 14-04), *and* `node_helper.js` defensively re-defaults it on every socket receive with `products?.showExcessiveRain === true`, plus initializes `this._products` in `start()`. Rationale: this exactly mirrors the existing `_updateInterval` / `_proximityWeighting` handling in the same method, it is the V5 input-validation control RESEARCH.md's Security Domain section calls for (a non-boolean truthy value must not enable a fetch path), and it means a stale or hand-edited frontend config cannot leave `this._products` undefined and crash the ERO gate.

- **A toggled-off product is EXCLUDED from `anyStale`.** Every `anyStale = true` assignment in the ERO path lives strictly inside `if (this._products.showExcessiveRain) { ... }`. Rationale: D-04 says "ERO fetch results roll into `anyStale`" — a product that is never fetched has no fetch result. A disabled product setting the global stale banner would be actively misleading, and this mirrors how the existing `if (extended)` wrapper already confines fire-weather Day 3-8's `anyStale` contributions (RESEARCH.md Pitfall 5).

- **`products` object keys use the config flag name directly** (`products.showExcessiveRain`, not `products.excessiveRain`). Rationale: RESEARCH.md Assumption A3 and Open Question 2 — no translation layer is needed, and Phase 17's iteration list comes from the registry's `configFlag` field, which is independent of this wire naming.

- **The `SPC_DATA_RESULT` response transport stays the existing `[outlook, md]` positional array.** `excessiveRain` is a new sibling key *inside* `outlook`, next to `fireWeather` (D-02). Migrating to a named response object is explicitly Phase 18 scope; changing it here would exceed D-08 for zero benefit this phase.

- **Do NOT adopt Phase 18's `days`/`summary`/`sources` schema** (D-02). The block is flat `dayNRisk`/`dayNText`/`dayNColor`/`dayNValidTime` fields mirroring `fireWeather`'s naming.

- **`excessiveRain.dayNRisk` values are tier STRINGS** (`"NONE"`/`"MRGL"`/...), matching the day1-3 `risk` vocabulary — **not** fire weather's 0-3 integers. D-02 says the block mirrors `fireWeather`'s *field-name* shape; it does not import fire weather's numeric gate vocabulary. This distinction is what lets plan 14-04 satisfy ERO-03 with the existing `!= "NONE"` display gate.

## Trust Boundaries

Single-user local MagicMirror display appliance. No authentication, session, access-control, or multi-tenant surface exists in this module and none is invented below.

| Boundary | Description |
|----------|-------------|
| MagicMirror frontend -> node_helper (socket) | User-supplied `lat`, `lon`, and the new `products` toggle object cross a local process-to-process notification channel |
| node_helper -> mapservices.weather.noaa.gov | Outbound HTTPS GET; the response body is external data parsed as JSON and fed to turf |

Note: the ERO query carries **no user coordinates** — the whole layer is fetched and point-in-polygon is evaluated locally, so `lat`/`lon` never reach the network on this path. `lat`/`lon` are therefore not part of any URL this plan constructs.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-01 | Tampering | ERO URL construction in `getSpcOutlook` | mitigate | `node_helper.js` constructs no query string at all — the single ERO call site is `ero.buildUrl(d)`, whose guards (integer `layerId`, NOAA host allowlist, fixed 3-param template) live in `productRegistry.js` from plan 14-01. Acceptance criteria assert `grep` finds no `mapservices.weather.noaa.gov`, no `f=geojson`, and no `f=json` literal anywhere in `node_helper.js`. |
| T-14-02 | Tampering | ERO coordinates reaching turf | mitigate | Every ERO fetch goes through `buildUrl`, which hardcodes `f=geojson` and therefore delivers WGS84 degrees; raw `f=json` (Web Mercator meters, silently wrong turf math) is unreachable. Plan 14-01 Task 3 verified max coordinate magnitude <= 180 on the wire for all five layers. |
| T-14-03 | Tampering | `products` object from a stale or hand-edited frontend config | mitigate | `this._products = { showExcessiveRain: products?.showExcessiveRain === true }` — strict boolean equality, not truthiness, so `"false"`, `1`, `{}`, or any other non-boolean resolves to `false` and cannot enable a fetch path (ASVS V5). `this._products` is additionally initialized in `start()`, so a payload with no `products` key leaves a defined object rather than crashing the gate. |
| T-14-04 | Denial of Service | Malformed or oversized ERO GeoJSON reaching `JSON.parse` in `fetchGeoJsonCached`, or a feature with a missing/odd `properties` object reaching `ero.toValue` | accept, with bounded blast radius | The ERO code runs inside `getSpcOutlook`'s existing outer try/catch, so a parse or property-access throw becomes a `{ error }` payload the frontend already renders as an error line — it cannot crash the node_helper process. `ero.toValue`'s `|| 0` fallback makes an absent or unmapped `dn` degrade to "no risk" rather than throw. Explicit response-size caps and network timeouts remain a documented pre-existing project-wide gap (`.planning/codebase/CONCERNS.md`, "No Network Timeout Configuration") applying equally to all existing fetches; fixing it here would exceed D-08 and stack unrelated risk. No new *untimed* fetch mechanism is introduced — every ERO call goes through the existing `fetchGeoJsonCached`. |
| T-14-05 | Spoofing | NOAA endpoint identity | mitigate (partial) | Host is an absolute `https://` literal in `productRegistry.js` with no user-controllable component, enforced by the builder's host allowlist; Node's default CA validation applies. | T-14-06 | Information disclosure | User location leaking to NOAA | mitigate (by design) | The ERO query is a whole-layer fetch with `where=1%3D1`; `lat`/`lon` are never placed in a URL, header, or request body.
