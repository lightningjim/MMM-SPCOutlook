<objective>
Generalise `fetchGeoJsonCached`'s hardcoded body-shape check into an injectable, defaulted
parameter, and add the four pure HeatRisk transform helpers (validator, zip, dedupe, day-offset).

Purpose: this is the phase's prerequisite edit. `fetchGeoJsonCached` today rejects any body without
a top-level `features` array (`node_helper.js:2193`, `:2209`), and the HeatRisk identify response's
features live at `body.catalogItems.features` — so without this change HeatRisk would present as a
permanent, silent fetch failure on every poll, forever. Doing it in its own plan, ahead of the
runner, means the "every existing caller is unchanged" proof gets its own acceptance criteria
rather than being buried inside a feature plan.

Output: `node_helper.js` gains one changed signature, two changed lines, and four new pure helpers
that 17-04's runner composes. No behaviour reaches any user in this plan.
</objective>

  <action>
    Add three pure helper methods to `node_helper.js`, placed together, immediately after
    `_hazardDayOffset` so every day-offset-adjacent function lives in one region.

    `_zipHeatRiskCatalog(body)` — D-06's zip-before-sort:
      - Read `features = body.catalogItems.features` and `values = body.properties.Values`
        defensively (the caller has already run `_isHeatRiskIdentifyResponse`, but this function
        must not throw on a body that slipped through).
      - Precondition guard: if `values` is not an array, or `values.length !== features.length`,
        return `null`. `null` is D-06's abandon signal, and 17-04 turns it into the all-null block
        plus `anyStale` plus a once-only log. Explicitly comment the two REJECTED alternatives and
        why: zipping to the shorter length front-truncates and silently mis-attributes every
        surviving pair (a confidently wrong category on the wrong day, strictly worse than showing
        nothing); falling back to the top-level `value` as Day 1 is wrong because that field
        tracks `catalogItemVisibilities`, which live capture on 2026-08-31 showed pointing at the
        Day-2 tile, not Day 1.
      - Otherwise return `features.map((f, i) => ({ attrs: f && f.attributes, rawValue: values[i] }))`.
      - Comment the load-bearing property: the tuple is built BEFORE any sort, so no positional
        index survives into the sort and a `catalogItems`/`Values` desync becomes unrepresentable
        rather than something later code must guard against.
      - This function MUST NOT sort. Sorting happens in the runner, after dedupe.

    `_dedupeHeatRiskByValidTime(tuples)` — HEAT-04:
      - Fold into a `Map` keyed by `attrs.idp_validtime`. Skip (`continue`) any tuple whose
        `idp_validtime` is not a finite number — a malformed item is dropped, contained, never
        thrown, exactly as `_hazardMatchesFromHits` drops a hit with a non-numeric `start_date`.
      - On a key collision, keep the tuple whose `attrs.idp_filedate` is greater, treating a
        missing/non-finite `idp_filedate` as `-Infinity` so a well-stamped item always beats an
        unstamped one.
      - Return `Array.from(map.values())`. Do not sort here either.
      - Comment the tiebreak choice and why `catalogItemVisibilities` is NOT used: live capture
        confirms it marks the single tile behind the top-level scalar `value`, so for a duplicate
        pair that is not also the globally visible tile both members read `0` — an unreliable
        per-pair signal. `idp_filedate` (present and independently varying on every item, ~15-min
        spread observed across the 7 items in one poll) is the tiebreak.

    `_heatRiskDayOffset(idpValidTimeMs, todayUtcMs)` — HEAT-01/02:
      - Delegate to `this._hazardDayOffset(idpValidTimeMs, todayUtcMs)`. Do not restate the
        formula; a second copy of `Math.round((epochMs - todayUtcMs) / MS_PER_DAY)` is exactly the
        two-places-declare-one-rule defect `daySpanOf`'s comment condemns and 16-REVIEW WR-03
        filed.
      - Comment why no `+1` adjustment is needed: every observed `idp_validtime` sits at exactly
        `12:00:00.000Z` (14/14 features across two live sessions), half a day past UTC midnight,
        so `Math.round(0.5) === 1` places today's tile at day key 1 and the mapping is stable
        across an entire UTC calendar day rather than only at the moment of capture. Note that
        this depends on the 12:00Z alignment holding — if a future response ever carries a
        midnight-aligned `idp_validtime`, this assumption breaks and the wrapper is where to fix
        it.
      - The wrapper exists so the HeatRisk call sites read HeatRisk-specific and so the 12:00Z
        rationale has one home; it must route through `_todayUtcMs()`/`_nowMs()` seams (via its
        caller) and never call `Date.now()` directly.
  </action>
