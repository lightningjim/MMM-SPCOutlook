     Both plans state it identically — if they ever diverge, the divergence is the bug. -->

spcrisk.heatRisk = {
  day1: { category, text, color },
  ... through day7
}

category  integer 0-4 exactly as the service reported it, OR null when that day had no resolved
          reading (a "NoData" pixel value, a missing catalog tile, or D-06's guard tripped).
          null and 0 are DELIBERATELY DISTINCT: 0 means "Little to No Risk" was affirmatively
          reported; null means HeatRisk had no reading at all. Phase 18's MERGE-03 depends on
          telling those apart, so the frontend must never coerce one into the other.
text      PRODUCT_REGISTRY.heatRisk.valueToText[category], or "" when category is null.
color     PRODUCT_REGISTRY.heatRisk.valueToColor[category] — 6 hex digits, NO leading '#'
          (matches this file's existing `"color:#" + value` concatenation) — or "" when null.

The block is emitted on EVERY poll regardless of showHeatRisk (Phase 14 D-05). Toggle off => all
seven days carry category null. The frontend must tolerate the whole block being absent
(version skew from an older helper), exactly as enabledAdvisories() and hazardsOutlookHasAnyDay
already tolerate their blocks being absent.

DISPLAY FLOOR (D-01, frontend-only per D-02):
  showMinorHeat === true  -> floor 1 (Minor and above render)
  otherwise               -> floor 2 (Moderate and above render)
