### Gaps Summary

**Limb 1 (UAT-5, the phase's MAJOR/headline defect) is not fixed.** The mechanism shipped by plan
19.1-03 (CSS `inline-block;min-width:Nch` column boxes plus a `wrapper.style.maxWidth = "32.4rem"`
region cap) is correctly implemented and does not regress any of the column-alignment invariants it
was built to preserve — but the cap value itself was derived from content needs alone and was never
checked against the deployed hardware's actual available space. Live measurement on 2026-09-10 shows
the shipped 648px cap overshoots the screen centreline by 168px on a rotated 1080x1920 display with
a ~450-480px true budget. The remedy is a mechanism change (replace character-advance/monospace
alignment with CSS-grid or fixed-layout-table alignment), not a cap-value tuning — a narrower `rem`
number cannot satisfy both the 54-column content need and the ~450px budget simultaneously while the
alignment mechanism still requires a monospace stream. The operator has already chosen this remedy
direction and recorded it in `19.1-LIVE-CHECK.md`; the `gaps:` entry above carries every measured
number and the rejected alternatives forward so the gap-closure planner does not have to re-derive
them.

**Limbs 2 (product-neutral copy) and 3 (config-key surfacing) are achieved**, each with one precise
caveat: neither limb's positive-path behaviour has been observed live on the deployed mirror (limb 2
because the deployed config sets an explicit header, so the fallback never fires there; limb 3
because the deployed config's key is spelled correctly, so the warn-and-suggest path was never
triggered there). Both are otherwise fully and independently confirmed at the code level in this
report (direct execution, source inspection, and re-run of the mutation-proven probe suite), and
limb 3's negative case (no false positive) IS confirmed live. Neither caveat blocks the phase, and
both are the honest, non-inflated claim strength the phase's own documents already record.

**Two minor, non-blocking findings** (not gaps): `detailColoredSpan` is dead code (defined, never
called) since plan 19.1-03's mechanism swap; and `19.1-UI-SPEC.md`'s Typography section still
asserts `font-family` is "never on an ancestor," which the shipped row-level declaration
contradicts — a reconciliation plan 19.1-05 was scoped to make but explicitly deferred. Both are
recorded for the record; neither requires action before the gap-closure phase, and the second folds
naturally into that phase's work since it is replacing the mechanism in question anyway.
