## Accomplishments

- `_levenshtein(a, b)` — standard iterative DP edit distance, `String()`-coerced inputs so a non-string key can never throw. No dependency added; `package.json`/`pnpm-lock.yaml` untouched (verified via `git diff --name-only`).
- `_nearestKnownConfigKey(key, knownKeys)` — returns the nearest `defaults` key under `max(2, ceil(key.length/3))`, or `null` when nothing is close enough (e.g. `latitude` → `lat` at distance 5 exceeds threshold 3). First-declared key wins ties via strict `<`.
- `_warnUnrecognizedConfigKeys()` — called as the first statement in `start()`, before `GET_SPC_DATA` is sent. Allowlist is exactly `Object.keys(this.defaults)` (14 keys); MagicMirror's own per-module keys (`hiddenOnStartup` etc.) are verified absent from the allowlist source. One `Log.warn` per unrecognised key, naming the key and — when close enough — the suggested match. Never logs `this.config[key]`. Never throws; a config typo degrades, it does not brick the mirror.
- **Rule 1 fix (see Deviations):** `resolveUpdateInterval()`, `buildRequestPayload()`, and `start()`'s diagnostic `Log.info` line all dereferenced `this.config` unguarded and threw a `TypeError` when `this.config` was `null` — a scenario the plan's own Task 2 `<verify>` command and Task 3's Scenario C both require `start()` to survive. Guarded all three with the same `typeof this.config === "object" && this.config !== null` check `_warnUnrecognizedConfigKeys` already uses.
- Three new probe scenarios, each individually mutation-proven (evidence below), added immediately after the `uat11-*` pair from plan 19.1-01.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `start()` threw a TypeError with `this.config = null`**

- **Found during:** Task 2, running the plan's own `<verify>` command (`run(null)` inside the automated check).
- **Issue:** `resolveUpdateInterval()` read `this.config.updateInterval`, `buildRequestPayload()` read `this.config.lat`/etc., and `start()`'s diagnostic `Log.info` line read `this.config.lat`/`.lon`/`.extended` — all three unguarded. With `this.config = null`, each threw `TypeError: Cannot read properties of null`. The plan's Task 2 acceptance criterion ("Behavior assertion (never throws): ... with `this.config = null`, `start()` completes without throwing") and Task 3's Scenario C sub-case (1) both require this exact call to survive.
- **Fix:** Added `const config = typeof this.config === "object" && this.config !== null ? this.config : {};` at the top of `resolveUpdateInterval()` and `buildRequestPayload()`, and an equivalent local in `start()` before the `Log.info` line, then read the local instead of `this.config` directly in each. Behavior for a valid config object is byte-identical; only the null/non-object path changed, from throw to graceful degradation (a fallback empty object, which itself feeds `resolveUpdateInterval`'s existing NaN-fallback-to-60 logic and yields `undefined` fields in the built payload — never a crash).
- **Files modified:** `MMM-SPCOutlook.js`
- **Commit:** `a4c2c55`

None of Task 1 or Task 3's own code needed a fix beyond this one; Task 3's mutation corrections (below) were execution-order adjustments, not code defects.
