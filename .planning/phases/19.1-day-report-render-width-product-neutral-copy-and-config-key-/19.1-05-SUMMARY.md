## What actually happened (read this before anything else in this phase)

Plans 19.1-01 through 19.1-04 landed cleanly and were deployed to the Pi byte-identical (all four
code markers confirmed present, SHA256 match). The operator then authorised flipping
`dayReportDetail: false → true` on the live config — overriding this plan's own
`<deploy_constraints>` — so the every-day width observation could actually run.

**Items 1 and 2 of the live check FAILED.** The day report still crosses the centreline; compact
rows still look displaced. Item 3 (no wrapping observed) is the diagnostic clue that reveals *why*:
the widest unbreakable run in a detail row (~433px) sits comfortably under the 648px cap, so the
cap was never actually reached — the region is 648px wide because the cap *permits* it to be, not
because the content demands it.

**Root cause, measured on the host (`ssh mm`, 2026-09-10):** the MagicMirror display is ROTATED —
1080 wide × 1920 tall, not the assumed landscape orientation. Usable content width after 60px body
margins on each side is 960px. There is no `top_center` module; the layout is two columns
(`top_left`/`top_right`), and the "centre column" 19-UAT test 5 describes is the LEFT column's own
territory. The right region (`top_right`, holding this module) spans x=372 to x=1020 at the shipped
648px cap, against a screen centreline at x=540 — a **168px overshoot**. The containment budget is
**W ≤ 480px** (or ~450px with a module gap).

**The derivation's actual error** (`MMM-SPCOutlook.js:1224-1236`, unchanged this plan): the cap was
computed purely from CONTENT NEEDS — 54 monospace characters × ~0.6em advance = 32.4em — and never
cross-checked against AVAILABLE SPACE. No value derived that way can be correct by construction. It
happens to land at 648px on a host that can afford at most ~480px.

**The monospace/`ch` coupling is the real mechanism-level finding, not a tuning input.** Alignment
by character advance requires a monospace stream (`ch` resolves per-element against its own font).
450px of DejaVu Sans Mono at the host's 20px root fits 37 characters; the column contract needs 54.
Monospace's uniform 0.602em advance costs roughly 30% more width than the host's proportional
Roboto Condensed would for the same 54 columns — almost exactly the shortfall. **Shrinking the
field widths would only partially buy this back; the mechanism itself is the cost.**

**Operator's decision, verbatim:** "Escalate to gap closure." Phase 19.1 closes as `gaps_found`
with the root cause recorded; the mechanism replacement (layout-based alignment — CSS grid or a
fixed-layout table, dropping the monospace dependency entirely, fitting ~450px at full 20px type)
is planned as its own gap-closure phase rather than bolted onto this plan's Task 3.

## What the gap-closure phase must do

1. **Replace character-advance alignment with layout-based alignment** (CSS grid or a fixed-layout
   table) for the detail-row column contract, so the ~450-480px budget can be met at the host's full
   20px root font size without a monospace dependency. This was the remedy recommended and accepted
   by the operator at disposition time — see `19.1-LIVE-CHECK.md`'s "Disposition" section for the
   two alternatives considered and rejected (shrinking type to ~14px; cutting
   `DETAIL_LABEL_FIELD_WIDTH` toward ~15).
2. **Derive the new cap from measured available space first**, then check content needs against
   that budget — not the reverse. The measured binding constraints (1080×1920 rotated, 960px usable,
   centreline x=540, right-region anchor x=1020, budget ≤480px/~450px with gap) are recorded in
   `19.1-UI-SPEC.md`'s Region Containment section and must not be re-measured from scratch; they are
   host geometry facts, not derivation assumptions.
3. **Re-express, do not delete, plan 19.1-04's three `uat05-*` probe scenarios**
   (`uat05-wrapper-declares-both-region-containment-contracts`,
   `uat05-detail-fields-carry-no-space-run-padding-and-declare-a-ch-floor`,
   `uat05-co-winner-and-also-rows-derive-their-boxes-from-the-groups-own-width`). They correctly pin
   today's mechanism and encode real regression value; the replacement mechanism needs the same
   properties re-pinned in its own terms (no space-run padding, a declared floor/track width, boxes
   derived from the group's own content), not a bare deletion.
4. **A fresh live check on the same deployed hardware is required before any new cap can be trusted**
   — this session's own precedent (the 19-08 false-negative, and now this plan's own disproof)
   establishes that no width claim for this module may be treated as resolved without an on-hardware
   observation.
