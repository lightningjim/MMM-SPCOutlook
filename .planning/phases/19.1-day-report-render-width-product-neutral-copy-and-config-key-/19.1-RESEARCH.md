## Summary

Three independent, narrowly-scoped defects, all frontend-only (`MMM-SPCOutlook.js`, no
`node_helper.js` involvement): (1) the detail-mode day report's column-alignment mechanism forces a
large, unconditional minimum row width that MagicMirror's regions do nothing to contain, so the
region visually overlaps its neighbor; (2) two user-facing strings still say "SPC" for a module that
now aggregates seven NWS/NCEP products; (3) MagicMirror merges every key under a module's `config:`
block into `this.config` with no validation at all, so a typo'd key is silently absorbed and never
surfaces to the operator.

This research verified three things directly against the MagicMirror source installed on the target
Pi (`ssh mm`, MagicMirror 2.37.0) rather than relying on training-data assumptions: the region-sizing
CSS (no `.region` rule sets `width`, `max-width`, or `overflow` — regions shrink-wrap to content and
have no collision avoidance with siblings), the `getHeader()`/`this.data.header` contract (the base
`Module` class already returns `this.data.header` verbatim today, and header visibility is toggled by
a plain JS truthiness check on the returned string, not by any `undefined`-vs-`""` special case), and
the config-merge boundary (`this.config` is built from `Object.assign({}, this.defaults, data.config)`
— it **never** receives `module`/`position`/`header`/`classes`/`disabled`/`hiddenOnStartup`/
`animateIn`/`animateOut`/`configDeepMerge`, because those live under `this.data`, a separate object,
and only the nested `config:{...}` sub-object feeds `this.config`). This last point corrects
CONTEXT.md's own candidate allowlist — the validator does not need to allowlist any MagicMirror
per-module key at all, only the module's own `defaults` keys.

**Primary recommendation:** implement the width fix as two separate, complementary changes — (a)
replace literal-space `padEnd` padding inside `white-space:pre-wrap` spans with
`display:inline-block;min-width:Nch` (not a hard `width`) on the *same* existing `<span style="...">`
elements, keeping the monospace `font-family` colocated so `ch` resolves correctly and preserving
graceful overflow for unmapped long labels; and (b) give the wrapper `<div>` (the element that already
carries `wrapper.style.textAlign = "left"`) an explicit `max-width` so the region's shrink-to-fit
calculation is bounded instead of unconstrained. Ship the getHeader() fallback and the config-key
validator as two small, independent, "warn and degrade" additions matching the existing
`resolveUpdateInterval()` idiom. Verify the width fix live on `ssh mm`; nothing else can prove it.

### Pattern 1: `min-width` + `display:inline-block` on the existing colored span (width fix)
**What:** Replace `labelContent.padEnd(DETAIL_LABEL_FIELD_WIDTH)` / `dimensionField.padEnd(...)`
(literal-space padding baked into escaped text) with a CSS box that has a guaranteed floor width but
still grows for the rare over-long unmapped label — i.e. `min-width`, not a hard `width`.
**When to use:** Any column that must both (a) align across rows for the common case and (b) never
truncate/clip a hazard label to force alignment (Degradation & Truncation's "never silently hide a
hazard" rule).
**Example (illustrative, not verbatim code to paste):**
```html
<!-- Today (defect): -->
<span style="color:#e06666;white-space:pre-wrap;font-family:'DejaVu Sans Mono','Liberation Mono',monospace">Convective Moderate               </span>   — SPC

<!-- Recommended: box carries the width, text carries no padding -->
<span style="color:#e06666;display:inline-block;min-width:23ch;white-space:nowrap;font-family:'DejaVu Sans Mono','Liberation Mono',monospace">Moderate</span>   — SPC
```
Per CSS Box Sizing / Intrinsic Sizing: an element with a definite, non-`auto` size in an axis
contributes *that* size (not a content-derived size) to an ancestor's shrink-to-fit computation in
the common case; content that exceeds a fixed `width` with `overflow:visible` (the default) paints
outside the box without enlarging it `[CITED: developer.mozilla.org/en-US/docs/Web/CSS/box-sizing]`.
Using `min-width` rather than `width` deliberately keeps the CURRENT graceful-degradation behavior
(today, `padEnd` is a silent no-op once content exceeds the field — WR-04's own comment says the
60-char truncation bound is the only limit) — `width` (hard) would instead need `overflow:hidden` to
avoid overlapping the next field, which conflicts with "never silently hide a hazard."

### Pattern 2: Explicit `max-width` on the wrapper div (region containment)
**What:** `wrapper.style.maxWidth = "<value>"` alongside the existing `wrapper.style.textAlign =
"left"` (`MMM-SPCOutlook.js:1059`).
**When to use:** This is the piece that actually stops the *region* from claiming more horizontal
space than intended. Verified directly from the MagicMirror CSS installed at HEAD on the target Pi
(`~/MagicMirror/css/main.css`, MagicMirror 2.37.0): `.region { position: absolute; }` plus only
directional insets (`top`/`right`/`bottom`/`left`) — **no** `.region` rule anywhere in the stylesheet
sets `width`, `max-width`, or `overflow`. For a `position:absolute` box with `width:auto` and no
`max-width`, the used width is computed via CSS2.1 §10.3.7's shrink-to-fit formula
`min(max(min-content, available), max-content)`; because MagicMirror gives the region essentially
the whole page as "available width" (no sibling collision avoidance exists at all — regions simply
paint on top of one another when they overlap), shrink-to-fit resolves to `max-content` (the
no-wrap width) whenever that's smaller than the page, which is exactly the observed defect: the
detail block's own preferred (unwrapped) width becomes the region's width, regardless of which
padding mechanism produced that preferred width. Giving the **wrapper** div an explicit `max-width`
caps its own contribution to that calculation directly and predictably, forcing the browser to WRAP
long rows instead of widening the region — this is the mechanism most directly responsible for
"does not widen its region," independent of the column-alignment mechanism chosen. `[VERIFIED:
official MagicMirror 2.37.0 source at ~/MagicMirror/css/main.css and ~/MagicMirror/js/main.js on the
target Pi via ssh mm]`

**Open risk, surfaced honestly:** capping `max-width` narrow enough to avoid overlapping the center
region may force a genuinely wide detail row (indent + 13-char dimension field + 23-char label field
+ attribution, ≈ 40–50 monospace characters) to wrap onto a second physical line, which conflicts
with the Detail-Mode Density spec's "each sub-row should stay exactly one physical line" rule. Rough
order-of-magnitude estimate `[ASSUMED — approximate monospace metric, not measured]`: at the root
`--font-size: 20px` declared in `main.css` and a typical ~0.6em advance width for monospace fonts
like DejaVu Sans Mono, ≈50 monospace characters ≈ 50 × 0.6 × 20px ≈ 600px — a substantial fraction of
a typical display's width, easily enough to overlap a center region depending on the module's
configured `position`. **This cannot be resolved by mechanism choice alone.** See "Open Questions"
below — the planner should budget for either (a) measuring the actual available region width live on
`ssh mm` and picking a `max-width`/field-width combination that fits it, or (b) a UI-SPEC amendment
that reduces `DETAIL_LABEL_FIELD_WIDTH`/`DIMENSION_FIELD_WIDTH` (permitted — CONTEXT.md locks "23 is
exact, do not round" only for the *current, literal-padding* mechanism; a mechanism change is
explicitly invited to amend the spec, per CONTEXT.md's own instruction to "make the amendment
explicitly").

### Pattern 3: `getHeader()` fallback (product-neutral header, D-02/D-03/D-04)
**What:** Add a `getHeader` method to the `Module.register(...)` definition object.
**Verified base-class behavior** (`~/MagicMirror/js/module.js:119-120`, MagicMirror 2.37.0):
```javascript
// Module.prototype (base class) — MMM-SPCOutlook.js inherits this today, unoverridden:
getHeader () {
  return this.data.header;
}
```
This is why an operator's `header: "SPC FORECAST"` line already renders today with zero code in this
repo — the base class passes it through verbatim. The phase's actual new code is the **fallback**:
```javascript
// Recommended shape — MMM-SPCOutlook.js, inside Module.register(...):
getHeader: function () {
  if (this.data.header === undefined) return "NWS Hazard Outlooks"; // D-03 umbrella name
  return this.data.header; // operator-configured value, including "" (D-04 opt-out)
}
```
`this.data.header` is verified `undefined` when the operator's config.js entry has no `header:` key
at all (`~/MagicMirror/js/loader.js:124`: `header: moduleData.header` — a JS property read that is
`undefined` when the source object literal lacks the key) and is the literal `""` when the operator
writes `header: ""`. **Header visibility is NOT gated by this `undefined`-vs-`""` distinction at
all** — it is gated by a separate, plain truthiness check in `~/MagicMirror/js/main.js`'s
`updateModuleContent()` (the function that runs on every real content refresh):
```javascript
// ~/MagicMirror/js/main.js:223-230 (paraphrased structure, verified verbatim on the Pi)
headerWrapper[0].innerHTML = newHeader;
if (headerWrapper.length > 0 && newHeader) {
  headerWrapper[0].style.display = "block";
} else {
  headerWrapper[0].style.display = "none";
}
```
Both `undefined` and `""` are falsy, so both already suppress the header region under the *base*
`getHeader()` — D-04's opt-out therefore requires no new machinery beyond returning `""` verbatim
when the operator explicitly set it, exactly as CONTEXT.md predicted, now confirmed against source.
`[VERIFIED: MagicMirror 2.37.0 source, ~/MagicMirror/js/module.js and ~/MagicMirror/js/main.js on
target Pi via ssh mm]`

**Minor, unrelated core quirk worth knowing (not this phase's concern):** the *initial* DOM creation
path (`~/MagicMirror/js/main.js`'s `createDomObjects()`, run once at boot before the first
`updateDom()`) sets `moduleHeader.style.display = "none;"` / `"block;"` — both invalid CSS values
because of the trailing semicolon, which browsers silently ignore, leaving the header's initial
display at the CSS default (`block`, per the `header { ... }` rule in `main.css`, which sets no
`display` override) until the first real `updateDom()` call corrects it via `updateModuleContent()`.
This is a pre-existing MagicMirror core bug unrelated to any module and out of this phase's scope —
noted only so a first-frame flash of an empty header row on cold boot is not mistaken for a
regression introduced by this phase's `getHeader()` fallback.

### Pattern 4: Config-key validator (D-13-equivalent, "Claude's Discretion")
**What:** In `start()`, alongside the existing `resolveUpdateInterval()` call
(`MMM-SPCOutlook.js:48-59` — the module's own established "warn once, degrade, never throw" idiom for
user-supplied config), compare `Object.keys(this.config)` against `Object.keys(this.defaults)`.
**Verified merge boundary** (`~/MagicMirror/js/module.js:212-230`, MagicMirror 2.37.0):
```javascript
setData (data) {
  this.data = data;                                  // header/position/classes/disabled/etc. live HERE
  ...
  this.setConfig(data.config, data.configDeepMerge);  // ONLY data.config feeds this.config
},
setConfig (config, deep) {
  this.config = deep
    ? configMerge({}, this.defaults, config)
    : Object.assign({}, this.defaults, config);
}
```
`data.config` is the raw `config:{...}` sub-object exactly as the operator wrote it in `config.js`
(`~/MagicMirror/js/loader.js:124`: `config: moduleData.config`) — unfiltered, unvalidated. Both the
shallow (`Object.assign`) and deep (`configMerge`) merge paths copy **every** key present in that
object onto `this.config`, whether or not the module's `defaults` recognizes it — this is exactly how
the deployed `dayReportDetails` (plural) typo reached `this.config.dayReportDetails` as a live,
silently-ignored property while `this.config.dayReportDetail` stayed at its default.

**This corrects CONTEXT.md's candidate allowlist.** CONTEXT.md's discretion section listed `module`,
`position`, `header`, `classes`, `disabled`, `hiddenOnStartup`, `config`, `configDeepMerge`,
`animateIn`, `animateOut` as keys the allowlist must additionally cover "or every real config
produces false warnings" — verification shows none of these ever reach `this.config`. They are
consumed into `this.data` by `setData()` before `setConfig()` even runs, and `setConfig()` only ever
sees `data.config` (the nested sub-object). **The validator therefore only needs
`Object.keys(this.defaults)` as its allowlist** — nothing else. This is a meaningfully simpler design
than CONTEXT.md anticipated, and it is also more correct: if an operator ever mis-nests `header:`
*inside* `config:{}}` by mistake, that genuinely does nothing (MagicMirror never reads
`this.config.header` for the header region), so flagging it as unrecognized is the right behavior,
not a false positive that a wider allowlist would have needed to suppress.
```javascript
// Recommended shape, mirroring resolveUpdateInterval()'s warn-once idiom:
validateConfigKeys: function () {
  const known = Object.keys(this.defaults);
  const unknown = Object.keys(this.config).filter((k) => known.indexOf(k) === -1);
  for (const key of unknown) {
    const suggestion = nearestKnownKey(key, known); // see Pattern 5 below
    Log.warn(
      "MMM-SPCOutlook: unrecognized config key " + JSON.stringify(key) +
      (suggestion ? ` — did you mean ${JSON.stringify(suggestion)}?` : "") +
      ". This key is ignored; it is not one of this module's defaults."
    );
  }
}
```
Call once from `start()`. Log the key **name** only, never `this.config[key]`'s value (see Security
Domain below — an operator could, in principle, mistype a sensitive-looking value under a bogus key
name; logging only the name avoids ever echoing config content to `mm-out.log`).

### Pattern 5: Dependency-free nearest-match suggestion (Levenshtein)
**What:** A small, standard iterative Levenshtein distance function — no package needed.
```javascript
// ~15 lines, vanilla JS, no dependency. Standard dynamic-programming edit distance.
function levenshtein(a, b) {
  const m = a.length, n = b.length;
  const d = Array.from({ length: m + 1 }, (_, i) => [i, ...Array(n).fill(0)]);
  for (let j = 0; j <= n; j++) d[0][j] = j;
  for (let i = 1; i <= m; i++) {
    for (let j = 1; j <= n; j++) {
      d[i][j] = a[i - 1] === b[j - 1]
        ? d[i - 1][j - 1]
        : 1 + Math.min(d[i - 1][j], d[i][j - 1], d[i - 1][j - 1]);
    }
  }
  return d[m][n];
}
function nearestKnownKey(key, knownKeys) {
  let best = null, bestDist = Infinity;
  for (const k of knownKeys) {
    const dist = levenshtein(key, k);
    if (dist < bestDist) { bestDist = dist; best = k; }
  }
  // Threshold: reject a "nearest match" that isn't actually close (avoids "did you mean
  // lat?" for a wildly unrelated typo). dayReportDetails -> dayReportDetail is distance 1.
  return bestDist <= Math.max(2, Math.ceil(key.length / 3)) ? best : null;
}
```
`[ASSUMED — standard algorithm, not sourced from any specific library; correctness is
self-verifiable by unit-testing the exact `dayReportDetails`/`dayReportDetail` case, distance 1]`.
This is the module's own restatement convention already in effect elsewhere (see "Established
Patterns" in CONTEXT.md's `<code_context>`: "Frontend/backend restatement over sharing" — this is the
same shape, a small self-contained helper rather than a dependency).

### Anti-Patterns to Avoid
- **CSS Grid or `<table>` for the column alignment.** Both require introducing a new element type
  (`<div style="display:grid">`, `<table>`/`<tr>`/`<td>`) that the harness's
  `INERT_MARKUP_ALLOWLIST` (`scripts/probe-lib/module-stubs.js:337-342`) does not permit — it only
  allows `<br/>`, `</span>`, `</i>`, `<span style="...">`, `<i class="...">`. Every frontend probe
  scenario calls `renderDom()` → `assertInertMarkup()`, so introducing either construct would throw
  in all 100+ existing frontend scenarios unless the harness's allowlist is also edited — a
  significantly larger, riskier change than `inline-block` on the *existing* `<span style="...">`
  tag shape, which needs no harness change at all (the regex matches any `style` attribute content,
  so adding `display:inline-block;min-width:23ch` to an existing span's style string still matches
  `^<span style="[^"<>]*">$` unchanged).
- **A hard `width` (not `min-width`) on the label/dimension field.** Combined with the default
  `overflow:visible`, an overflowing unmapped/long label would render its overflow UNDER/behind
  whatever the *next* sibling box paints (layout does not shift to accommodate visual overflow),
  producing overlapping garbled text for exactly the "60-character unmapped label" case the current
  code already handles gracefully via `padEnd`-as-no-op. `min-width` avoids this: the box grows to
  fit long content, pushing later siblings right, matching today's degrade-gracefully behavior.
- **Deriving `alsoIndent`'s width from a rendered string's `.length` under the new mechanism as a
  drop-in swap.** WR-02 (iteration 4, locked) derives the `also:` indent from `dimensionField.length`
  — the group's own *rendered* width — specifically to handle an unmapped dimension name that
  overflows `DIMENSION_FIELD_WIDTH`. Once the dimension field becomes a CSS `min-width` box rather
  than a literal-padded string, `dimensionField.length` (a JS string length) no longer numerically
  equals the box's *visual* rendered width for the overflow case (a monospace character ≈ 1ch only
  when the box is unconstrained; the box's `min-width` floor and its content's overflow width can
  now diverge from a simple character count in ways this string-based renderer has no way to measure
  — there is no `getBoundingClientRect()` available, this is pure string concatenation). For the
  **common case** (label fits within the field), `dimensionField.length` post-truncation still
  matches the intended `ch` count and the existing derivation continues to work unchanged. For the
  **rare unmapped-overflow case**, the `also:` row's indent may drift out of visual alignment with
  its winner row by a few characters — flag this as an accepted, rare-case cosmetic degradation (the
  UI-SPEC's own "Degradation & Truncation" section already accepts exactly this class of tradeoff for
  the current mechanism), not a defect to solve with more machinery.

## Common Pitfalls

### Pitfall 1: Neither `jsdom` nor `linkedom` can prove the width fix
**What goes wrong:** A tempting "closing the loop" move is to add a real-DOM devDependency so a probe
scenario can assert the rendered width numerically.
**Why it happens:** `renderDom()` in `scripts/probe-lib/module-stubs.js` currently returns markup
text, not layout, and the existing `rpt03-*` scenarios assert column *indices* in that markup —
exactly the gap that let this defect ship green (123 passing scenarios, 0 catching the overflow).
**How to avoid:** Both mainstream lightweight DOM libraries considered explicitly document that they
do not implement CSS layout: jsdom's own README states "Layout: the ability to calculate where
elements will be visually laid out as a result of CSS... jsdom currently [returns] zeros for many
layout-related properties" `[CITED: raw.githubusercontent.com/jsdom/jsdom/main/README.md]`; linkedom's
README states it does not implement CSS layout/box-model/`getBoundingClientRect` and explicitly
recommends Playwright for real layout needs `[CITED:
raw.githubusercontent.com/WebReflection/linkedom/main/README.md]`. Neither would let a probe scenario
compute `ch`-to-pixel conversion, shrink-to-fit width, or overlap detection. The only mechanisms a
probe *can* prove here are structural/negative: assert the emitted markup no longer contains a
literal multi-space run baked into escaped text where a CSS width declaration should be (e.g., after
`escapeHtml`, the label span's text content should `.trim()` to itself — no leading/trailing padding
characters), and assert the style attribute of the relevant span contains `min-width` with a `ch`
unit. Both are mutation-provable (reintroduce `.padEnd(...)` in source, confirm the new scenario goes
RED with a diagnosable message). The actual overlap-vs-region question stays `MANUAL ONLY`, verified
on `ssh mm`, exactly as CONTEXT.md's own specifics section already states.
**Warning signs:** Any plan task that says a probe scenario "confirms the width fix" without a
`MANUAL ONLY` companion row on the parity checklist is repeating the exact failure this defect
already demonstrated once.

### Pitfall 2: Mechanism change alone does not guarantee the region shrinks
**What goes wrong:** Assuming that switching from literal-padding to CSS `inline-block`/`ch` widths
by itself narrows the region, because "CSS is more correct."
**Why it happens:** For the *common* case (a short label, well within the field), both mechanisms
produce a box of essentially the same visual width (the field-width numbers, 23/13, don't change
just because the mechanism does) — the win from switching mechanisms is *predictability and
allowlist-compatibility*, not automatically less total width. The actual region-overlap defect is
caused by MagicMirror's shrink-to-fit resolving to the row's *unconstrained* preferred width (no
sibling collision avoidance, no `.region` `max-width` — verified above), which an explicit `max-width`
on the wrapper div addresses directly, independent of which column-alignment mechanism is chosen.
**How to avoid:** Treat "column alignment mechanism" and "region width containment" as two separate
changes (Patterns 1 and 2 above) — do not assume shipping only Pattern 1 closes UAT test 5.
**Warning signs:** A plan whose only change is inside `renderDaySubRows`/the winner-row/`also:`-row
builders, with no change to the wrapper div's own style, is very likely repeating the same
"aligned but still too wide" outcome UAT test 5 already reported once (its own `partial_pass` note:
"alignment and co-winner fixes hold; the defect is block width").

### Pitfall 3: Breaking `assertInertMarkup`'s allowlist with a new tag
**What goes wrong:** Introducing a `<div>` (for a per-day wrapper, or a CSS Grid container) or a
`<table>`/`<tr>`/`<td>` set anywhere the width fix touches.
**Why it happens:** Both are natural reaches for "real" column layout in general web development.
**How to avoid:** `INERT_MARKUP_ALLOWLIST` (`scripts/probe-lib/module-stubs.js:337-342`) permits only
`<br/>`, `</span>`, `</i>`, `<span style="[^"<>]*">`, `<i class="[^"<>]*">`. `assertInertMarkup()`
runs on every frontend scenario via `renderDom()` and throws on the first disallowed tag shape. The
`inline-block` recommendation in Pattern 1 deliberately reuses the existing `<span style="...">` tag
shape so no harness change is needed at all.
**Warning signs:** Any diff touching this phase that also touches `module-stubs.js`'s allowlist
should be treated as a signal the render mechanism drifted from the recommendation above — that's a
strictly larger, riskier change than this phase's stated scope.

### Pitfall 4: `ch` unit resolving against the wrong font
**What goes wrong:** Declaring `width:23ch` on an element whose `font-family` is NOT the monospace
stack (e.g., putting the width on the outer wrapper span, which inherits Roboto Condensed, rather
than on the inner colored span that already carries `font-family:'DejaVu Sans Mono',...`).
**Why it happens:** `ch` is defined as "the advance measure of the glyph `0` in the element's own
font" `[CITED: developer.mozilla.org/en-US/docs/Web/CSS/length]` — it resolves per-element, not
inherited from an ancestor's computed `ch` value. A width declared on an element with the default
proportional font would size against Roboto Condensed's `0` glyph width, not DejaVu Sans Mono's,
silently breaking the alignment the whole mechanism exists to provide.
**How to avoid:** Verified current code already colocates `font-family` and (today) the `pre-wrap`
declaration on the *same* span (`detailColoredSpan`, `MMM-SPCOutlook.js:418-421`) — keep the new
`width`/`min-width` declaration on that exact same `style` attribute, not on the outer wrapper span
or a new element.
**Warning signs:** Any code that declares a `ch` width on a different element than the one carrying
`font-family:'DejaVu Sans Mono'...` needs a second look.

### Pitfall 5: Config-key validator logging a value, not just a key name
**What goes wrong:** A well-intentioned debug-friendly warning that logs `JSON.stringify({[key]:
this.config[key]})` to help the operator see what's wrong.
**Why it happens:** Natural instinct when building a "helpful" warning message.
**How to avoid:** Log only the key **name** and the nearest-match suggestion (Pattern 4's example
does this). An operator's config is user-authored and not validated by MagicMirror in any way
(`WR-05`'s own comment block, `MMM-SPCOutlook.js:42-47`) — nothing prevents a future config key from
holding something the operator wouldn't want in a shared `mm-out.log`. This mirrors T-19-class
Info-disclosure threats already tracked in `19-SECURITY.md` for other value-echoing surfaces.
**Warning signs:** Any warning message that interpolates `this.config[key]` rather than just `key`.

## Open Questions

1. **Does the target region actually have enough available width for the current 23+13-character
   field budget, even after the mechanism fix?**
   - What we know: the region itself imposes no width cap (verified from MagicMirror's own CSS); the
     detail row's *content* width (indent + dimension field + label field + attribution) is roughly
     40-50 monospace characters regardless of which mechanism produces it; the operator's live
     screenshot shows real overlap into the center column at whatever the module's actual configured
     `position` and the center region's actual content currently occupy.
   - What's unclear: the actual number of pixels available before the center region's content starts,
     on the specific deployed layout — this is genuinely deployment-specific and was not (and cannot
     be, from this research session) measured without rendering on the real hardware.
   - Recommendation: the planner should treat "measure the real available width on `ssh mm` before
     picking a `max-width` value" as a required task, not an optional nicety, and should be prepared
     to either accept occasional wrapping on the widest rows or amend the UI-SPEC's field-width
     numbers (permitted under CONTEXT.md's own instruction to amend the spec for a mechanism change)
     if the measured width can't accommodate the current budget without wrapping.

2. **Should `also:` row indentation under the new mechanism use a matching CSS `min-width` spacer
   span, or restate the same numeric distance as a fixed `ch` value?**
   - What we know: WR-02 (locked) currently derives `alsoIndent` from `dimensionField.length` — the
     group's own rendered width — specifically to keep the `also:` row aligned with an unmapped
     dimension that overflowed the nominal field width.
   - What's unclear: under a `min-width`-box mechanism, there is no `getBoundingClientRect()`-style
     measurement available to this string-concatenation renderer, so an overflowing dimension field's
     *actual visual* width can no longer be derived the same way for the rare overflow case (see
     Anti-Patterns above).
   - Recommendation: keep the current derivation for the common (non-overflowing) case (it still
     numerically agrees with the box's `min-width` there), and accept the rare-overflow-case
     misalignment as a documented, accepted cosmetic degradation — consistent with the UI-SPEC's own
     existing stance on this exact class of edge case.

3. **Exact wording for the README's aggregation description (D-05).**
   - What we know: the README today says only "SPC Point-in-Polygon check for location in Outlooks"
     (`README.md:2`) plus a "Multiple instances" section — it never lists the seven products by name.
   - What's unclear: whether D-05's "sweep covers... the README's description of what the module
     aggregates" wants a full product list restated in the README, or just the same NWS umbrella
     wording used in the header/loading-string fallback.
