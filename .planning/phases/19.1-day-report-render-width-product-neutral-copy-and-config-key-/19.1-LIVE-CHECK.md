## Root Cause — the cap was derived without reference to available space

Items 1, 2 and 3 together refute the "wrong cap value" reading and identify a derivation error.
Measured on the deployed host, 2026-09-10:

| Quantity | Measured value | Source |
|---|---|---|
| Panel geometry | **1080 wide x 1920 tall** — the display is ROTATED (`HDMI-A-1 connected 1080x1920+0+0 left`; native mode 1920x1080) | `xrandr` on the Pi |
| Body margins | 60px left, 60px right (`--gap-body-left/right`) | `~/MagicMirror/css/main.css` |
| Usable content width | **960px** | 1080 - 60 - 60 |
| `rem` basis | 20px (`html { font-size: var(--font-size) }`, `--font-size: 20px`) | `main.css` lines 8, 21-26 — the 32.4rem derivation's assumption is CORRECT; `rem` really is 20px here |
| Cap as rendered | 32.4rem = **648px** | derivation x rem basis |
| Right region span | **x = 372 to 1020** (`.region.right { right: 0 }`, shrink-to-fit leftward from the body's right edge at 1020) | `main.css` line 178-179 |
| Screen centreline | x = 540 | 1080 / 2 |
| **Overshoot past centre** | **168px** | 540 - 372 |

There is no `top_center` module in the deployed config: the layout is two columns, `top_left`
(clock, calendar, MMM-Nightscout) and `top_right` (MMM-PirateSkyForecast, weather x2,
MMM-SPCOutlook). The "centre column" of 19-UAT test 5 is the LEFT column's territory. At a 648px
cap the right region consumes 648 of the 960 usable pixels (67.5%), leaving 312px for the entire
left column.

**Why no wrapping (item 3):** the widest unbreakable run in a detail row is the two adjacent
`inline-block` boxes emitted with no whitespace between them — `detailFieldBox(13ch) +
detailFieldBox(23ch)` = 36ch = ~433px. That is comfortably UNDER the 648px cap, so nothing wraps.
The cap is simply never reached. The region is 648px wide because the cap permits it to be, not
because the content demands it.

**The derivation's actual error** (`MMM-SPCOutlook.js:1224-1236`): the cap was computed from
CONTENT NEEDS — 2 + 13 + 23 + 3 + 1 + 1 + 11 = 54 monospace chars x ~0.6em = 32.4em — and never
cross-checked against AVAILABLE SPACE. No value derived that way can be correct by construction;
it happens to land at 648px on a host that can afford at most ~480px.

**Budget for containment:** for the right region to stop at the centreline, W <= 1020 - 540 =
**480px**; with a `--gap-modules` (30px) separation, **~450px**.

**The monospace cost (operator's own hypothesis, 2026-09-10 — "The monospace itself might be part
of the problem"):** confirmed quantitatively. 450px of DejaVu Sans Mono at the 20px root is
450 / (0.602 x 20) = **37 characters**. The layout needs 54. Monospace's uniform 0.602em advance —
paid in full by every `i`, `l`, `.` and space — costs roughly 30% width against the host's
proportional Roboto Condensed (~0.42em average for mixed text, ~455px for the same 54 columns at
full 20px). The ~30% monospace premium is almost exactly the shortfall. The mechanism is not
incidental: plan 19.1-03 introduced the row-level monospace declaration precisely BECAUSE the `ch`
unit resolves per-element (RESEARCH.md Pitfall 4), so the column contract is currently
alignment-by-character-advance, which REQUIRES a monospace stream. Fixing the width therefore
means either shrinking the type, narrowing the fields, or replacing character-advance alignment
with layout-based alignment (grid/table) that does not need monospace at all.

**Consequence for this plan:** items 4/5/6 did not regress, so this is not the column-alignment
code defect that Task 2 says to stop for. But items 1 and 2 FAIL means the phase goal — the
day report no longer overlapping — is NOT achieved, and the remedy is a derivation change plus
a mechanism decision, not a `narrower: <value>` nudge of the existing formula.
