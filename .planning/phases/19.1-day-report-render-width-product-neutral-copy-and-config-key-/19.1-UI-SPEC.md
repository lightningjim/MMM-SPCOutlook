## Design System

Unchanged from `19-UI-SPEC.md` §Design System (no build step, no framework, host-inherited font,
`weather-icons` only).

**Decision made this phase (closing 19-UI-SPEC's open question): no stylesheet.** All new styling
stays inline, on the existing per-span `style="..."` convention. `getStyles()` (`:222`) continues
to return only `weather-icons`; no new entry is added. The `ch`-based mechanism below needs no
selector — `min-width` is fully expressible as an inline declaration on the same spans that
already carry `color`/`font-family` inline. Introducing a CSS file was considered and rejected:
it would be a new build/load pattern for zero mechanism benefit (Pattern 1 works identically
inline), and it isn't needed to fix any of this phase's three defects.

## Layout Grammar

### Detail line — Column contract (AMENDED mechanism, unchanged field widths)

**What is retired:** the "character offsets, measured from the left margin" framing and its
"this is the exact number; do not round or approximate it" lock on `DETAIL_LABEL_FIELD_WIDTH = 23`
as a *literal padded character count*. That framing is what produced the UAT-5 defect —
`padEnd()` inside a `white-space:pre-wrap` span sets a hard, non-collapsing min-content width
that MagicMirror's region has no mechanism to contain. The framing is wrong as a *rendering*
instruction, not as a *design* one.

**What survives unchanged:** the field-width VALUES. `DIMENSION_FIELD_WIDTH` (`:385-387`, derived
from `DIMENSION_LABELS`' longest value + 1) and `DETAIL_LABEL_FIELD_WIDTH = 23` (`:391`) are still
derived the same way, for the same reason (a future taxonomy addition widens the field
automatically). Only the mechanism that turns those numbers into visual alignment changes: from
literal trailing spaces baked into escaped text, to a CSS box with a guaranteed floor width.

**SUPERSEDED (gap closure, plan 19.1-06).** The table and paragraphs immediately below (through the
end of "Resolving the `also:` indent") describe the `display:inline-block;min-width:Nch` mechanism
this amendment introduced. That mechanism is preserved here verbatim, as history, because it is what
plan `19.1-05`'s live check on real hardware measured and disproved (`19.1-LIVE-CHECK.md` Root
Cause) — it required a monospace character stream that could not fit the layout's 54-column need
inside the deployed host's ~450px budget at the host's full 20px root font size. It does **not**
describe the shipped mechanism. The replacement contract (CSS Grid) is stated after this preserved
block, below "Resolving the `also:` indent."

**New column contract (SUPERSEDED — see above):**

| Element | Mechanism | Notes |
|---|---|---|
| Dimension name field | `<span style="display:inline-block;min-width:{DIMENSION_FIELD_WIDTH}ch">` wrapping the truncated, **unpadded** dimension name | Replaces `dimensionField.padEnd(DIMENSION_FIELD_WIDTH)` (`:607`). No content padding — the box supplies the floor width. |
| Label field | `<span style="display:inline-block;min-width:{DETAIL_LABEL_FIELD_WIDTH}ch">` wrapping the truncated, **unpadded** label content (+ D-07 proximity suffix) | Replaces `labelContent.padEnd(DETAIL_LABEL_FIELD_WIDTH)` (`:645`). WR-04's truncate-then-pad order becomes **truncate, then box** — truncation still happens on the entry's own source text before it ever reaches the box; the box only supplies width, it never re-touches the string. |
| Co-winner blank dimension field (BL-02) | Same dimension-name-field span, empty content, same `min-width` | Replaces `"".padEnd(dimensionField.length)` (`:618`). An empty inline-block box of the same floor width reads as blank exactly as a run of literal spaces did. |
| Color/font-family carrier | Stays on the **outer** `detailColoredSpan` wrapper (`color`, `font-family:'DejaVu Sans Mono',...`); the new inline-block field spans nest inside it, with no `color` attribute of their own (they inherit it) | Preserves "dimension name and label share one color" (D-02) — the visual color unit is unchanged; only its internal structure gains two nested width-bearing spans. Preserves Pitfall 4's requirement that `ch` and `font-family` are colocated: the nested spans inherit `font-family` from the exact same ancestor that already carries it, so `ch` still resolves against DejaVu Sans Mono, not the host's Roboto Condensed. |
| `also:` indent spacer (WR-02 iteration 4) | `<span style="display:inline-block;min-width:{2 + max(DIMENSION_FIELD_WIDTH, dimensionField.length) + 2}ch"></span>` (empty, uncolored) | Replaces `" ".repeat(2 + dimensionField.length + 2)` (`:665`). See "Resolving the also: indent" below — this is the same formula WR-02 already uses, only re-targeted at a CSS width instead of a space count. |
| `also:` label field | Same mechanism as the winner's label field, same `alsoLabelFieldWidth` derivation (`:669`), unchanged | No change beyond the mechanism swap already described above. |

**Harness compatibility (Pitfall 3):** every element above is an existing `<span style="...">`
tag shape with an extended `style` value. `INERT_MARKUP_ALLOWLIST` (`module-stubs.js:337-342`)
matches on tag shape, not style-attribute content, so `display:inline-block;min-width:13ch` inside
an existing span's `style="..."` needs **no harness change**. Do not introduce `<div>`, CSS Grid,
or `<table>`/`<tr>`/`<td>` anywhere in this fix — any of those breaks the allowlist in every
existing frontend scenario (Pitfall 3, RESEARCH.md Anti-Patterns).

**Overflow behavior (this is the ambiguity the old character-count contract could not express —
resolved here):**
- **Field-level overflow** (an unmapped dimension name or label longer than its field, 18 D-07's
  shipped path): the box **grows to fit the content** (`min-width` is a floor, not a ceiling) and
  pushes the source attribution right. This is a **push-right, never a wrap, never a clip** —
  identical to today's `padEnd`-as-no-op behavior for this exact case. No regression, no new
  degradation; the mechanism swap is invisible here.
- **Row-level overflow** (the whole detail row, including an overflowed field, is wider than the
  wrapper's `max-width` — see "Region Containment" below): the row **wraps onto a second physical
  line** at the browser's normal inline break points. This is new only in the sense that it is now
  *possible* — under the old, unconstrained-region mechanism, an overflowing row inflated the
  region instead of wrapping (the UAT-5 defect itself). This is an accepted, rare-case degradation
  of Detail-Mode Density's "each sub-row stays exactly one physical line" rule, already scoped to
  the overflow case that rule's own text anticipates ("the probabilistic sub-line is the one place
  a wrap is expected" — extended here to any row whose content genuinely cannot fit).

**Resolving the `also:` indent (RESEARCH.md Open Question 2 — resolved, not deferred):**
WR-02 (iteration 4, locked) derives `alsoIndent` from `dimensionField.length` — the group's own
*rendered* width — specifically so an overflowing dimension name doesn't detach the `also:` rows
from the winner row above them. RESEARCH.md flagged this as potentially drifting under a CSS
mechanism because there is no `getBoundingClientRect()` available to a string-concatenation
renderer. **This drift does not occur here**, because `ch` is defined as the advance width of the
`0` glyph *in the element's own font*, and every glyph in a monospace font shares that same advance
width by definition (`[CITED: developer.mozilla.org/en-US/docs/Web/CSS/length]`). So
`max(DIMENSION_FIELD_WIDTH, dimensionField.length)` expressed as a `ch` value on an inline-block
spacer reproduces the exact same visual width WR-02's literal-space formula already computes —
the formula is unchanged, only its unit changes from "N literal space characters" to "N ch." No
new machinery, no accepted degradation, on this one point.

**Replacement column contract (gap closure, plan 19.1-06 — current, shipped mechanism):**

The mechanism above is superseded by CSS Grid. Column alignment is no longer a property of a
character stream; it is a property of the row's own `grid-template-columns`, declared identically
on every row kind (winner, co-winner, `also:`), which is what keeps columns aligned ACROSS rows
without any shared parent grid.

- **Row container:** the existing row `<span>` gains `display:inline-grid`, `box-sizing:border-box`,
  `width:100%`. `padding-left:0.6rem` (`DETAIL_ROW_INDENT_REM`) replaces the retired literal `"  "`
  two-space indent; `column-gap:0.4rem` (`DETAIL_COLUMN_GAP_REM`) replaces the retired literal
  `"   "` three-space attribution gap; `align-items:baseline` keeps text baselines aligned across
  the three cells the way inline text naturally would. `inline-grid`, not block-level `grid`: the
  row stays inline-level so the trailing `<br/>` row terminator keeps its existing meaning.
- **Three tracks, declared identically on every row kind:**
  `grid-template-columns: minmax(0,{dimension}fr) minmax(0,{DETAIL_LABEL_FIELD_WIDTH}fr)
  minmax(0,{SOURCE_ATTRIBUTION_FIELD_WIDTH}fr)`. `minmax(0,Nfr)`, never a bare `Nfr`, is
  load-bearing: a grid item's automatic minimum size is `auto`, which would let a long unbreakable
  word push its own track — and therefore the row — wider than the container; flooring the minimum
  at `0` forces overflowing content to wrap INSIDE its own track instead.
- **`SOURCE_ATTRIBUTION_FIELD_WIDTH` is NEW** and is derived from `SOURCE_SHORT_NAMES`' own longest
  mapped value + 2 (the `"— "` prefix), following the exact same derive-never-hardcode rule
  `DIMENSION_FIELD_WIDTH` already follows — a future source addition widens this track
  automatically instead of silently truncating a longer short name against a stale constant.
- **Colour carrier:** `detailColoredWrapper` now declares `display:contents` — its own box is
  removed, so its two child cells (dimension name, label) become grid items of the enclosing row
  directly, while still inheriting `color` from the wrapper (an inherited property does not need a
  box to travel through). Phase 19 D-02 ("the dimension name and the label share one colour") is
  preserved exactly: one `validHazardColor` call, one colour decision, two cells.
- **BL-02, restated for the grid:** the co-winner's blank dimension field is an EMPTY CELL in the
  same track as every other row's dimension cell, not an empty inline-block box of a computed width.
  **WR-02 iteration 4, restated:** all three row kinds (winner, co-winner, `also:`) derive their
  first track's `fr` value from the single quantity `Math.max(DIMENSION_FIELD_WIDTH,
  dimensionField.length)`, computed exactly once and reused, never restated per row kind.
- **Retired, and why:** `alsoIndent` and `alsoLabelFieldWidth` — both were arithmetic that kept the
  `also:` row's em dash on the winner row's own column under the inline-block mechanism. The shared
  grid track now guarantees that alignment structurally, so arithmetic that could drift (RESEARCH.md
  Open Question 2's own concern) was replaced by a contract that cannot drift by construction.
- **Harness compatibility, restated as the resolution of the central tension:** the superseded
  paragraph above's instruction against `<div>`/CSS-Grid/`<table>`/`<tr>`/`<td>` (quoted verbatim,
  unmodified, above) remains preserved as history, and it remains binding for
  `<div>`/`<table>`/`<tr>`/`<td>`. It was **over-broad** about CSS Grid: Grid is
  a style-attribute property VALUE, not a tag. `display:inline-grid` on the existing
  `<span style="...">` shape delivers layout-based alignment while `INERT_MARKUP_ALLOWLIST`
  (`module-stubs.js:337-342`), which matches on tag shape rather than style-attribute content, stays
  byte-identical — confirmed empirically (`19.1-06-SUMMARY.md`: `git diff --exit-code
  scripts/probe-lib/module-stubs.js` exits 0). This is proven by execution, not merely asserted, in
  plan `19.1-07`'s `wr07-assert-inert-markup-accepts-module-tags-and-rejects-everything-else`
  scenario, whose `<div>` mutation goes RED against the same allowlist that accepts every grid-based
  span this mechanism emits.
- **Overflow behaviour — replaces the two bullets in the superseded section above:**
  - **Field-level overflow** no longer pushes the source attribution right. `minmax(0,Nfr)` floors
    every track at zero, so an over-long dimension name or label **wraps INSIDE its own cell**
    (`detailFieldCell`'s `overflow-wrap:anywhere`) and the row's declared tracks are unchanged. This
    is a genuine behaviour change from the retired push-right rule, stated here rather than glossed
    over: the retired mechanism's box grew to fit content and pushed later fields right; the
    replacement's box never grows past its track, and long content wraps in place instead.
  - **Row-level overflow can no longer inflate the region at all**, because the row is
    `width:100%` of a wrapper that is itself capped (see "Region Containment" below) — a row cannot
    contribute a max-content width larger than its own container, by construction.

### Region Containment (NEW — a separate, independent contract from column alignment)

**This is not satisfied by the column-alignment fix above.** RESEARCH.md Pattern 2/Pitfall 2 are
explicit: for the common case, both the old and new column mechanisms produce a row of essentially
the same preferred width, because the field-width *numbers* (13, 23) don't change. Shipping only
the column-alignment fix reproduces UAT test 5's own finding — "alignment and co-winner fixes
hold; the defect is block width." **A plan that lands the column mechanism above without this
section is incomplete.**

**The mechanism:** `wrapper.style.maxWidth` set on the same wrapper `<div>` that already carries
`wrapper.style.textAlign = "left"` (`:1059`, the shipped 19-08 gap closure for right-hand
MagicMirror regions). Set both in the same place; do not remove or weaken the `textAlign` anchor —
it is unrelated (it fixes indentation direction for right-hand regions; `max-width` fixes shrink-
to-fit sizing) and both are required simultaneously.

```javascript
wrapper.style.textAlign = "left";       // unchanged (19-08)
wrapper.style.maxWidth = "32.4rem";     // NEW — ≈650px at the host's 20px root; see derivation
                                        // and required live-tuning below
```

**Unit: `rem`, not a bare `px` literal (UI-checker Dimension 5 recommendation, applied).** The
derivation below produces `54 characters × ~0.6em advance = 32.4em` of monospace text, and only
becomes a pixel figure by multiplying through the host's root `--font-size: 20px`. Expressing the cap
as `32.4rem` states the derivation directly instead of its arithmetic product: the number in the code
is now the same quantity the derivation computes, and the cap tracks the host's root font-size if
MagicMirror's `--font-size` is ever changed (a px literal would silently stop matching the text it is
sized to contain). `rem` is correct here where `ch` is not — `ch` resolves against the *element's own*
font, and this wrapper contains both monospace detail rows and proportional compact-line/band content,
so a `ch` cap would resolve ambiguously depending on which child it was measured against. `rem`
resolves against the root regardless of which child is widest.

**Why `max-width` on the wrapper, not a width on any inner span:** verified against the MagicMirror
2.37.0 source installed on the target Pi — `.region` sets no `width`/`max-width`/`overflow`
(`~/MagicMirror/css/main.css`), so a `position:absolute` region with `width:auto` resolves via
CSS2.1 §10.3.7's shrink-to-fit formula to its content's `max-content` width whenever that's smaller
than the page — which is exactly the observed defect. The wrapper is the only element this module
controls that sits directly inside the region; capping *its* contribution to that shrink-to-fit
calculation is the only lever available (Pattern 2).

**Derivation of the starting value (`[ASSUMED — must be live-tuned, see below]`):** the worst-case
*common-case* (non-overflowing) detail row is `2 (indent) + DIMENSION_FIELD_WIDTH (13)
+ DETAIL_LABEL_FIELD_WIDTH (23) + 3 (attribution gap) + 1 (em dash) + 1 (space)
+ longest SOURCE_SHORT_NAMES value` monospace characters — roughly 54 characters at the widest
mapped source name ("WPC Hazards", 11 chars). Using the root `--font-size: 20px` variable
(`main.css`) and RESEARCH.md's own assumed ~0.6em monospace advance ratio (A1, `[ASSUMED]`),
54 × 0.6 = **32.4em of monospace text**, expressed in the code as `32.4rem` (≈ 650px at the host's
current 20px root). This bounds the detail row to *its own designed width* — a value derived from the
same taxonomy-driven constants as the field widths themselves, not a magic number — which is a
necessary cap regardless of where the center region happens to sit. If
`DIMENSION_FIELD_WIDTH`/`DETAIL_LABEL_FIELD_WIDTH` change during live tuning, recompute this figure
from the same formula rather than nudging the rem value independently; the two must not drift.

**What this derivation cannot promise, stated honestly (RESEARCH.md Open Question 1):** `32.4rem`
caps the detail row's *own* contribution to shrink-to-fit; it does not know how many pixels are
actually available before the *specific deployed* center region's content starts, because that is
deployment-specific and was not measurable from this research session. **Required verification
step, not optional:** measure the real available width live on `ssh mm` with `dayReportDetail:
true` active, and either confirm `32.4rem` clears the center column, or (permitted under this
amendment, same as CONTEXT.md's own instruction to amend the spec for a mechanism change) reduce
`DIMENSION_FIELD_WIDTH`/`DETAIL_LABEL_FIELD_WIDTH` and/or lower `max-width` further. This is the
one number in this document that is not fully specified by design alone — see "Verification
Honesty" below.

**SUPERSEDED (live check, 2026-09-10 — see `19.1-05-SUMMARY.md` and
`19.1-LIVE-CHECK.md`).** The derivation above is preserved verbatim so the history of why
`32.4rem` existed is not lost, but it does **not** stand. The live check did not merely find the
*value* wrong — it disproved the *method*. The derivation above computes `32.4rem` entirely from
CONTENT NEEDS (54 monospace characters × ~0.6em) and never cross-checks that figure against
AVAILABLE SPACE on the deployed region. A cap derived that way cannot be correct by construction;
it happens to land at 648px on a host that can afford at most ~480px. **Any replacement cap MUST
be derived from measured available space first, with content needs checked against that budget —
not the other way around.**

**Replacement derivation (gap closure, plan 19.1-06 — available-space-first, current mechanism):**

The replacement cap is derived in the opposite order from the superseded derivation above: measured
available space first, content needs checked against that budget second, never the reverse.

1. Measured geometry (`19.1-LIVE-CHECK.md`, `ssh mm`, 2026-09-10): the panel is 1080×1920 (rotated;
   native mode is 1920×1080), with 60px body margins on each side (`--gap-body-left/right`,
   `main.css`), giving 960px of usable content width. The root font-size is 20px (`--font-size`,
   `main.css`), so `1rem = 20px` here — the one assumption the superseded derivation got right, and
   it carries forward unchanged.
2. The body's right edge sits at x=1020 and the screen centreline at x=540. The **hard containment
   ceiling** is `1020 − 540 = 480px` (24rem) — the region must never cross this figure or it
   overlaps the centre column outright, by definition of where the centreline sits.
3. `--gap-modules` (30px) backs the working budget off from that hard ceiling, so this module and
   its neighbour are not flush against one another: `1020 − 540 − 30 = 450px`.
4. Converting at the measured 20px root: `450 / 20 = 22.5rem`. `wrapper.style.maxWidth =
   REGION_CAP_REM + "rem"` (`MMM-SPCOutlook.js:1298`) sets exactly this value.
5. Content is allocated INSIDE that fixed 450px/22.5rem budget by the grid-track builders' `fr`
   tracks (see "Detail line — Column contract" above), never the reverse: the budget is fixed
   first, and the tracks then divide whatever space already exists.

**The rule for any future cap, stated once:** available space first, content checked against it,
never the reverse. This is the single sentence the superseded derivation above violated.

`22.5rem` is `[PENDING LIVE CONFIRMATION — plan 19.1-09]`. The arithmetic above is verified against
measured host geometry, but no width claim for this module may be treated as resolved without an
on-hardware observation — this phase's own precedent, twice over (the 19-08 false negative, and
this phase's own disproof of `32.4rem`). Plan `19.1-09`'s live check on `ssh mm` is what confirms or
refutes this value; it is not confirmed here.

**Why this is a stronger containment guarantee than a cap alone:** under the superseded mechanism,
the cap was a permission the content might or might not use — the 648px cap did not CAUSE the
648px-wide region, it merely PERMITTED it, and the actual (unbounded) row's own preferred width
happened to fit comfortably under it (~433px), so the cap was never reached and the region grew to
whatever its unconstrained rows demanded, up to that permission. Under the replacement mechanism,
every detail row is `width:100%` of the (now-capped) wrapper, and its own tracks are zero-floored
(`minmax(0,Nfr)`), so a row's own max-content width can never exceed the wrapper's width in the
first place. The cap is now a bound the content CANNOT exceed, rather than a permission the content
may or may not use — stated plainly, this is exactly what the superseded mechanism got wrong: the
region was 648px wide because the cap permitted it, not because content demanded it.

**Measured host geometry (binding constraint for any replacement, measured 2026-09-10 on `ssh
mm`):**

| Quantity | Measured value |
|---|---|
| Panel geometry | 1080 wide × 1920 tall — the display is ROTATED (`xrandr`: `HDMI-A-1 connected 1080x1920+0+0 left`; native mode 1920×1080) |
| Body margins | 60px left, 60px right (`--gap-body-left/right`, `~/MagicMirror/css/main.css`) |
| Usable content width | 960px (1080 − 60 − 60) |
| `rem` basis | 20px (confirmed correct — the 32.4rem derivation's assumption about the root font-size was never the error) |

| Screen centreline | x = 540 (1080 / 2) |
| Overshoot at the disproven cap | 168px past centre |
| **Containment budget** | **W ≤ 480px** to reach the centreline (1020 − 540); **~450px** with a `--gap-modules` (30px) separation |

**The monospace/`ch` coupling (mechanism-level finding, not merely a tuning input):** alignment by
character advance — the mechanism `19.1-03` introduced, and the one this document's column
contract above specifies — REQUIRES a monospace stream, because `ch` resolves against the
element's own font (Pitfall 4) and only a monospace font gives every character the same advance.
That requirement has a measured cost: 450px of DejaVu Sans Mono at the host's 20px root fits **37
characters** (450 / (0.602em × 20px)); the layout's own column contract needs **54**. Monospace's
uniform 0.602em advance — paid in full by every `i`, `l`, `.` and space — costs roughly 30% more
width than the host's proportional Roboto Condensed would for the same 54 columns (~455px). That
~30% premium is almost exactly the shortfall between the 450px budget and the 648px shipped cap.
**Consequence:** the field-width numbers (13, 23) are not necessarily the problem; the alignment
*mechanism* is. Shrinking the type or narrowing the fields would each buy back some width without
addressing the mechanism cost; replacing character-advance alignment with layout-based alignment
(CSS grid or a fixed-layout table) removes the monospace dependency entirely and was the remedy
chosen for the gap-closure phase to plan — see `19.1-LIVE-CHECK.md`'s "Disposition" section.

**Interaction with the compact line and the band:** the wrapper's `max-width` applies to *all*
content this module renders, not only detail rows — the compact line's existing "no line-length
cap... let it wrap naturally" policy (19-UI-SPEC §Layout Grammar, unchanged) is not contradicted,
it is now *actually enforceable*: previously "wrap naturally" had no width to wrap within (the
region had none either), so an 8-segment compact line and an overflowing detail row shared the
same root cause. The band (advisories + window entries, 19-UI-SPEC §"The Band", unchanged wording
and position) wraps under the same cap for the same reason.

`19.1-VERIFICATION.md`'s Anti-Patterns Found row 2 recorded as an open, unreconciled contradiction
between this document and shipped code.

**Font-family is no longer declared anywhere in the detail-row markup.** The retired
inline-block/`ch` mechanism (see "Detail line — Column contract" above) required
`font-family:'DejaVu Sans Mono','Liberation Mono',monospace` colocated with every `ch`-based width
declaration, because `ch` resolves per-element against that element's own font (RESEARCH.md
Pitfall 4). The grid-track mechanism (`19.1-06`) declares no `ch` value anywhere — column widths
come from `fr` tracks on `grid-template-columns`, which resolve against the row's own box, never
against any font's glyph metrics — so the font-family requirement that motivated the original
reinforcement instruction no longer applies, and no replacement font-family declaration exists in
its place.

**Two-step history, stated so neither step reads as an unexplained reversal:** plan `19.1-03`
deliberately declared `font-family` at ROW level, contradicting `19-UI-SPEC.md`'s original "never
on an ancestor or a sibling" instruction, because the uncoloured `also:` indent spacer sat outside
every coloured span and needed an ancestor's `font-family` to resolve its own `ch` width correctly
(RESEARCH.md Pitfall 4; `19.1-03-SUMMARY.md`'s own "Assumption Drift" section records this as a
deliberate, spec-contradicting deviation, taken knowingly, not an oversight). The gap closure
(`19.1-06`) then removed `font-family` from the detail markup entirely, because grid tracks do not
resolve against a font at all — there is no `ch` value left anywhere in this markup for a
font-family declaration to serve.

**Scoped to `color` only, going forward:** the original sentence read "never on an ancestor or a
sibling" with no qualification. It now applies to `color` alone, which still lives on a single
carrier (`detailColoredWrapper`, via `display:contents`) and is never declared on an ancestor or a
sibling of the cells it colours. It makes no claim about `font-family` any longer, because no
length anywhere in this markup resolves against one.

**Visible consequence, reversed and flagged, not approved here:** detail rows now inherit the
host's own typeface (MagicMirror's proportional Roboto Condensed) rather than the monospace stack.
This reverses plan `19.1-03`'s own accepted visible consequence — the literal `also:` token and the
`— SPC` / `— WSSI` source attributions render in the host's proportional font again, not monospace.
This reversal is flagged here as an item for plan `19.1-09`'s live observation; it is recorded, not
approved, by this document.

## New Component: `getHeader()` Lifecycle Method (D-02/D-03/D-04)

Not a render-inventory item in the visual sense (MagicMirror paints it, this module doesn't
build markup for it) — documented here because it is a genuinely new user-visible surface with
its own three-state contract, verified against `~/MagicMirror/js/module.js`/`main.js` (2.37.0) on
the target Pi.

- **Trigger:** MagicMirror core calls `getHeader()` on every DOM update, then paints the returned
  string into the module's header region, toggling `display:block`/`none` on a plain truthiness
  check of that string (`~/MagicMirror/js/main.js`, `updateModuleContent()`).
- **Contract:** return `this.data.header` verbatim whenever it is a non-`undefined` value
  (covers both an operator's configured string AND an explicit `header: ""` opt-out — both are
  falsy and both already suppress the header region via MagicMirror's own truthiness check, no
  extra logic needed). Return the module's own neutral default (`"NWS Hazard Outlooks"`) only
  when `this.data.header === undefined` — the key is genuinely absent from `config.js`.
- **Never** override a configured header, regardless of its content.
- No inline styling, no new DOM structure — this is a plain string return, unaffected by the
  width/color/typography contracts above.

## New Component: Unrecognised-Config-Key Warning (Claude's Discretion, resolved)

Operator-facing, not on-screen — a `Log.warn` line in `mm-out.log`, read during troubleshooting
(the exact channel that cost the 2026-09-09 UAT session real time). Documented here because it is
the one genuinely new user-visible **output** this phase introduces outside the render itself.

- **Trigger:** once, at `start()` — mirrors `resolveUpdateInterval()`'s existing "warn and
  degrade, never throw" idiom (`:48-59`). No repeated logging on every poll; `start()` itself only
  runs once per module load, so no `_logged*` once-only guard is needed (unlike
  `resolveUpdateInterval`, which can be called on every interval tick).
- **Allowlist:** `Object.keys(this.defaults)` only. Verified against MagicMirror 2.37.0's
  `setData`/`setConfig` (`~/MagicMirror/js/module.js:212-230`): `module`/`position`/`header`/
  `classes`/`disabled`/`hiddenOnStartup`/`animateIn`/`animateOut`/`configDeepMerge` all live on
  `this.data`, never on `this.config` — they cannot produce a false positive and must **not** be
  added to the allowlist (a wider list than `this.defaults` is unnecessary machinery, not a safety
  margin).
- **Message shape:** name the unrecognised key AND its nearest `defaults` match (Levenshtein
  distance, threshold `max(2, ceil(key.length/3))` — see RESEARCH.md Pattern 5). A bare "unknown
  key" warning is explicitly insufficient — that is what the actual `dayReportDetails` vs
  `dayReportDetail` failure would have produced, and it would not have saved the UAT session.
  Example: `MMM-SPCOutlook: unrecognized config key "dayReportDetails" — did you mean
  "dayReportDetail"? This key is ignored; it is not one of this module's defaults.`
- **Never log the key's value.** Only the key name and the suggested match travel to
  `mm-out.log` (Pitfall 5) — a config value could hold anything, including something an operator
  would not want in a shared log.
- **Loudness:** `Log.warn`, never `Log.error`/throw. A config typo must not brick the mirror —
  distinct from `hazardTaxonomy.js`'s `assertTaxonomyIntegrity()` and `daySpanOf()`, which
  correctly throw at load time because they guard *static module-authored data*, not user input.

## Detail-Mode Density (one-sentence amendment)

**SUPERSEDED (gap closure, plan 19.1-06):** the paragraph immediately below described the retired
inline-block mechanism, under which a row-level overflow wrapped the WHOLE row onto a second
physical line. Preserved here as history; the shipped mechanism does not behave this way.

> Unchanged from `19-UI-SPEC.md` §"Detail-Mode Density" except: "each sub-row should stay exactly
> one physical line" now has one explicit, accepted exception — a row that overflows the wrapper's
> new `max-width` (Region Containment, above) wraps onto a second line rather than inflating the
> region. This is the same class of accepted degradation the section already grants the
> probabilistic sub-line; it is not a new policy, only an extension of an existing one to a case
> this amendment's fix makes newly possible (wrapping) instead of impossible (region inflation).

**Current behaviour (gap closure, plan 19.1-06):** under the grid-track mechanism, overflow is
absorbed by wrapping INSIDE a cell (`detailFieldCell`'s `overflow-wrap:anywhere` on a zero-floored
`minmax(0,Nfr)` track), never by the row as a whole. "Each sub-row stays exactly one physical line"
therefore holds for MORE cases than the retired mechanism could offer — a wrap inside a single
cell (which stacks that cell's own content onto more than one visual line, without moving the
row's other cells or inflating the wrapper) is now the sole remaining exception, alongside the
probabilistic sub-line this section already grants a stand-alone extra line.
