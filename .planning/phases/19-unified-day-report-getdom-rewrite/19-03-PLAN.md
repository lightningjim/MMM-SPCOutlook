<objective>
Give D-04's per-day auto-expand a real, declared trigger.

**Placement decision made at planning time, correcting RESEARCH.md and PATTERNS.md.** Both
documents place the `SIGNIFICANCE_FLOOR` table in `hazardTaxonomy.js` and describe the *frontend*
as consuming it per entry. The frontend cannot do that: `MMM-SPCOutlook.js` runs in the browser
and cannot `require("./hazardTaxonomy")` — CONTEXT.md establishes exactly this constraint for
`ADVISORY_SOURCES` ("The frontend cannot `require` the registry, so this mapping is stated, not
derived"). Restating a source-scoped threshold table in browser context would create a second
declaration of taxonomy data, which is the defect class `hazardTaxonomy.js` exists to prevent.

Therefore: the table lives in `hazardTaxonomy.js` where the rest of the taxonomy lives, the
backend evaluates it once per grid day after precedence resolves, and the payload carries a
resolved boolean `days[n].autoExpand`. The frontend stays a pure reader (RPT-07's framing) and
renders detail when `config.dayReportDetail === true || days[n].autoExpand === true`.

This is not new merge or precedence logic — it is a display hint derived from already-resolved
entries, computed where the taxonomy it reads already lives.

Purpose: unblock RPT-02/RPT-03's detail-mode trigger.
Output: `SIGNIFICANCE_FLOOR`, its integrity assertion, `days[n].autoExpand`, mutation-proven.
</objective>
