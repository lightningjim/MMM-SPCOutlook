# Phase 19.1 Plan 03: Day Report Render Width Fix Summary

**Replaced literal-space `padEnd()` column padding in the detail sub-row/also: renderers with `display:inline-block;min-width:Nch` boxes on the existing `<span style="...">` tag shapes, and capped the wrapper's `max-width` at `32.4rem` (alongside the existing `textAlign` anchor) so MagicMirror's shrink-to-fit region sizing stops growing to the row's full unconstrained width — the two independent halves 19.1-UI-SPEC.md's Region Containment section requires.**

## Accomplishments

- `detailFieldBox(widthCh, innerHtml)` — one builder, digit-sanitised (`String(Math.max(0, Math.trunc(Number(widthCh)) || 0))`) `min-width:Nch` box on an existing span shape. Never calls `escapeHtml` (escaping stays at the leaf, receives already-escaped content only).
- `detailColoredWrapper(color, innerHtml)` — the unescaped-content sibling of `detailColoredSpan`, emitting the identical opening/closing span but concatenating `innerHtml` verbatim so it can host the nested boxes without double-escaping. `detailColoredSpan` is re-expressed as `detailColoredWrapper(color, escapeHtml(content))` — one definition of the opening span, kept in place per the plan even though both of its own call sites were converted to `detailColoredWrapper` directly.
- Winner/co-winner rows: `dimensionField` keeps its own-account `truncateHazardLabel` but drops `.padEnd()`. One derived quantity, `dimensionFieldWidthCh = Math.max(DIMENSION_FIELD_WIDTH, dimensionField.length)`, drives the winner's dimension box, the BL-02 blank co-winner box (empty content, same floor width — never a `&nbsp;`/`.repeat()`/zero-width space), and the `also:` spacer (`2 + dimensionFieldWidthCh + 2`). WR-04's truncate-then-box order is preserved: `labelContent` is computed before it ever reaches `detailFieldBox`.
- `also:` rows: the literal-space `alsoIndent` is replaced by an empty, uncolored `detailFieldBox(2 + dimensionFieldWidthCh + 2, "")` spacer — same formula as before (`2 + … + 2`), only the unit changes from "N literal spaces" to "N ch". `alsoLabelFieldWidth`'s own derivation is unchanged.
- Row-level `font-family:'DejaVu Sans Mono','Liberation Mono',monospace` added to both row spans (winner and `also:`) — see "Assumption Drift" below, this is a deliberate, documented deviation from 19.1-UI-SPEC.md's Typography sentence.
- `wrapper.style.maxWidth = "32.4rem"` set immediately after the existing `wrapper.style.textAlign = "left"` (19-08 anchor), with the mechanism, the traceable derivation, and the `rem`-over-`px`/`ch` rationale recorded in a comment kept within the plan's 20-line adjacency requirement.
- Two named mechanism-dependent probe scenarios (`wr04-detail-label-truncation-counts-source-characters-not-padding`, `wr02-also-rows-column-with-the-winner-row-under-an-unmapped-dimension`) re-expressed against the new box markup, both mutation-proven. One collateral scenario (`bl02-two-co-equal-survivors-on-one-dimension-are-peers-not-also-rows`) also required re-expression — see Deviations.
- Suite: **187 passed, 0 failed, 0 skipped** — identical total to the end of plan 19.1-02 (no scenario added or removed).

## Assumption Drift (advisory)

- **Planned assumption (19.1-UI-SPEC.md Typography section):** "font-family... never on an ancestor" — implying the monospace declaration should live only on the innermost colored span (`detailColoredWrapper`), exactly where it lived before this plan (`detailColoredSpan`, unchanged).
- **What turned out true:** the plan's own Task 1 action item 3 (read during execution) explicitly requires the SAME font-family declaration to ALSO be added at the row-level span, one level higher than the colored wrapper — a documented exception to the Typography sentence.
- **Why:** the `also:` indent spacer and the literal `"  "`/`"also: "`/`"   — "` runs sit OUTSIDE the colored span entirely, in no span at all before this plan. `ch` resolves per-element against its OWN font (Pitfall 4), so without a font-family declaration on some ancestor, those literal runs (and the boxes' relationship to them) would compute against the host's proportional font while the boxes computed against DejaVu Sans Mono — breaking the character-stream alignment the whole mechanism exists to provide. The plan itself calls this out explicitly as "a DELIBERATE, documented deviation," so this is not a genuine drift from the plan's intent, only from the UI-SPEC prose it amends; recorded here per the advisory protocol since a reader of the UI-SPEC alone would not expect it. One visible consequence for plan 19.1-05's live check: the literal `also:` text and the `— SPC`-style attribution render monospace where they previously rendered proportional.
