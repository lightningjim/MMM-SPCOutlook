# Phase 19.1 Plan 04: Width Regression Guard Summary

**Added `renderDomWrapper()` to the probe harness (returning the stub wrapper object so style
assignments are observable) and three mutation-proven structural scenarios that pin the ABSENCE
of the UAT-5 defective construct (space-run padding) and the PRESENCE of both width contracts
plan 19.1-03 introduced — closing the exact gap that let 182 green scenarios miss a region-width
overflow defect (187 → 190 passing).**

## Accomplishments

- `renderDomWrapper(frontend, { config, spcrisk })` — additive harness accessor in
  `scripts/probe-lib/module-stubs.js`, placed immediately above `renderDom`. Builds `ctx`, calls
  `frontend.getDom.call(ctx)`, runs `assertInertMarkup` when `innerHTML` is non-empty, and returns
  the stub wrapper OBJECT. `renderDom` is re-expressed as a one-line delegation, so there is
  exactly one render path and `assertInertMarkup(wrapper.innerHTML` appears exactly once in the
  file (verified by grep) — all ~120 existing `renderDom` call sites are untouched. The accessor's
  own comment states, explicitly, that the `style` bag proves only that a property was ASSIGNED,
  never that a layout claim is true, and names the two properties it exists for (`textAlign`,
  `maxWidth`) plus the 19.1-UI-SPEC.md Verification Honesty rows it does not close.
  `INERT_MARKUP_ALLOWLIST`'s four regexes are byte-identical to their pre-plan form (confirmed:
  `git diff` shows no hunk touching that block); no dependency was added.
- `uat05-wrapper-declares-both-region-containment-contracts` — asserts `wrapper.style.maxWidth
  === "32.4rem"` and `wrapper.style.textAlign === "left"` with separate, individually-named
  failure messages, a vacuity guard (the render must have actually produced a detail sub-row), and
  a loading-branch control (both properties are assigned before the branch split, so a future
  refactor that moves them inside a branch fails loudly here too).
- `uat05-detail-fields-carry-no-space-run-padding-and-declare-a-ch-floor` — asserts (1) no
  space-run padding reaches the markup beyond two named, justified exemptions (the three-space
  attribution gap and `convectiveDetailAugment`'s five-space sub-line indent), (2) both
  `min-width:13ch`/`min-width:23ch` boxes are present, (3) every `min-width:` occurrence is
  preceded by the monospace `font-family` declaration in its own row (Pitfall 4), and (4) a
  200-character label still floors at `min-width:23ch` (a floor, not a ceiling) with no hard
  `width`/`overflow:hidden`/`text-overflow` reaching the markup. Includes a precondition guard and
  a compact-header control (the compact line carries no `min-width:` box at all).
- `uat05-co-winner-and-also-rows-derive-their-boxes-from-the-groups-own-width` — the first
  scenario to exercise a winner, a co-winner, and a suppressed competitor on ONE dimension
  together. Asserts BL-02's blank co-winner box stays an empty, immediately-closed span (never
  `&nbsp;`/spaces), the co-winner's label box matches the winner's own width, the `also:` spacer
  derives from the group's own width (`2 + 13 + 2 = 17` for this mapped fixture) and is itself
  empty and uncoloured, the literal `also: ` text stays outside any colour span, and the one
  derived quantity feeding all three boxes agrees with itself AND equals the concrete value `13`.
  Includes a precondition guard (all three row kinds must render) and a no-co-winner control.
- Suite: **187 → 190 passed, 0 failed, 0 skipped** (three scenarios added, none removed, none
  regressed).

### Notable in-plan adjustments (not Rule 1-4 deviations, recorded for traceability)

**1. Stale line-number citation in the plan's own action text.** The plan's Task 2 action names
`:490` for `convectiveDetailAugment`'s five-space sub-line indent exemption. At this plan's start
that indent literal lives at approximately line 630 — the citation predates line shifts from
intervening edits earlier in this wave (19.1-01/02/03). The new scenario's comment names the
function (`convectiveDetailAugment`'s `subLineHtml` literal) rather than a raw line number, so a
future reader is not misdirected and the comment cannot go stale the same way again. No code
behavior is affected; this is a comment-accuracy adjustment only.

**2. Task 2 Mutation 2's blast radius required removing font-family from a third call site.**
The plan's action text names two mutation targets ("the row span" and "detailColoredWrapper").
Removing font-family from only the winner row span and `detailColoredWrapper` produced a ZERO
blast radius beyond the new scenario itself: the pre-existing `wr07-hostile-token-in-every-
remote-string-still-renders-inert-markup` scenario's landmark check (`rendered.includes(
"font-family:'DejaVu Sans Mono'")`) still matched because the `also:` row's own, separately-
declared font-family (a third call site, unmutated) still appeared somewhere in that scenario's
much larger render. The plan itself states "a ZERO blast radius would be the defect" for this
exact mutation, so the font-family declaration was also removed from the `also:` row span for the
mutation-proof run (restored immediately after). This produced the expected non-zero collateral
failure (`wr07-hostile-token-...` also went RED), which is recorded below and does not change the
scenario's own code.

## What This Plan Does NOT Prove (stated explicitly, per its own scope)

None of the three scenarios added by this plan prove that the detail-mode region has stopped
overlapping the centre column, or that `32.4rem` is the correct cap value. They prove: (1) both
width-fix style contracts are assigned on the wrapper, (2) the defective space-run-padding
construct is absent and the `ch`-based mechanism is present and correctly colocated with its
required font-family, and (3) the shared derivation feeding the winner box, the BL-02 blank
co-winner box, and the `also:` spacer agrees with itself. The `style` bag exposed by
`renderDomWrapper` is a bare property bag — nothing in this harness lays out, measures, or
renders, so no scenario here (or anywhere in this suite) can compute `ch`-to-pixel conversion,
shrink-to-fit width, or visual overlap. That verification is `MANUAL ONLY` per
19.1-UI-SPEC.md's Verification Honesty rows 5-6, and is plan 19.1-05's job (the `ssh mm` live
measurement).
