**`detailFieldBox`** — the `min-width:Nch` box builder (`:541-550`):
```javascript
// T-19.1-9/T-19.1-17: detailFieldBox's innerHtml argument is ALREADY-ESCAPED markup or
// text — escaping stays at the LEAF, so this builder must never call escapeHtml itself.
// T-19.1-10/T-19.1-12: the width argument is sanitised digit-only
// (String(Math.max(0, Math.trunc(Number(widthCh)) || 0))), mirroring validHazardColor's
// posture for the one other value that reaches a style attribute — a payload-influenced
// string length can drive this number, but only digits can ever reach the attribute.
const detailFieldBox = (widthCh, innerHtml) => (
  "<span style=\"display:inline-block;min-width:" +
  String(Math.max(0, Math.trunc(Number(widthCh)) || 0)) + "ch\">" + innerHtml + "</span>"
);
```

### `scripts/probe-lib/module-stubs.js` — the harness constraint the mechanism choice must clear

**`INERT_MARKUP_ALLOWLIST`** (`:337-342`, verbatim, unchanged since Phase 19):
```javascript
const INERT_MARKUP_ALLOWLIST = [
  /^<br\/>$/,
  /^<\/(?:span|i)>$/,
  /^<span style="[^"<>]*">$/,
  /^<i class="[^"<>]*">$/
];
```
`assertInertMarkup` (`:363-373`) runs on every frontend scenario's rendered `innerHTML` via
`renderDomWrapper`/`renderDom` and throws on the first tag shape not matched above.

**`renderDomWrapper`** — the harness accessor plan 19.1-04 added, returning the stub wrapper
OBJECT (not markup) so a scenario can assert on `wrapper.style.*` (`:375-400`, verbatim):
```javascript
// Render a payload through the real getDom and return the resulting stub wrapper OBJECT
// (not its markup) so a scenario can observe properties assigned on it, e.g.
// wrapper.style.textAlign (the 19-08 right-region anchor) and wrapper.style.maxWidth (the
// region-containment cap) are the two properties this accessor exists to make observable.
// Both remain `MANUAL ONLY` for the layout claim itself — see 19.1-UI-SPEC.md's
// "Verification Honesty" table.
function renderDomWrapper(frontend, { config, spcrisk }) {
  const ctx = Object.create(frontend);
  ctx.config = config;
  ctx.spcrisk = spcrisk;
  ctx.updateDom = () => {};
  const wrapper = frontend.getDom.call(ctx);
  if (wrapper.innerHTML) assertInertMarkup(wrapper.innerHTML, "getDom innerHTML");
  return wrapper;
}
function renderDom(frontend, { config, spcrisk }) {
  const wrapper = renderDomWrapper(frontend, { config, spcrisk });
  return wrapper.innerHTML || wrapper.textContent || "";
}
```
`renderDomWrapper`'s own comment states explicitly what it can and cannot prove: a style
property was ASSIGNED, never that a layout claim is true. This accessor is directly reusable —
no change needed to observe whatever new style properties a layout-based mechanism assigns
(e.g. a `display:grid`/`display:table` value on the wrapper or a row element), as long as those
properties land on an object `renderDomWrapper` can already reach.

**THE CENTRAL TENSION the planner must resolve (mapped as fact, not decided here):**
`19.1-RESEARCH.md`'s own "Anti-Patterns to Avoid" and Pitfall 3 explicitly warn against `<div>`,
CSS Grid, or `<table>`/`<tr>`/`<td>` — "any of those breaks the allowlist in every existing
frontend scenario ... a significantly larger, riskier change than `inline-block` on the
*existing* `<span style="...">` tag shape." `19.1-UI-SPEC.md`'s "Detail line" section repeats
the same instruction near-verbatim. **`19.1-VERIFICATION.md`'s chosen remedy is exactly the
thing both documents warn against**: "REPLACE character-advance alignment with layout-based
alignment (CSS grid or a fixed-layout table)." This is not a contradiction to silently resolve —
it is the operator's own escalation decision, made *after* both documents were written, with
full knowledge that the monospace/`ch` coupling (not merely the field-width numbers) is the
actual defect. **If the planner's chosen mechanism introduces any tag shape other than
`<span style="...">`/`<br/>`/`<i class="...">`, `INERT_MARKUP_ALLOWLIST` (`:337-342`) will need a
new regex entry, and every one of the ~190 existing frontend scenarios that calls
`renderDom`/`renderDomWrapper` will re-exercise that new allowlist entry on its very next run —
this is expected fallout of the chosen remedy, not a regression to work around.**

scenario's *invariant* (one derived quantity feeds the winner box, the blank co-winner box, and

single most important assertion to preserve exactly — it is the WR-02/BL-02 review history this
codebase has broken and re-fixed multiple times (`19-REVIEW.md`/`19-REVIEW-FIX.md` iterations,
cited in `19.1-CONTEXT.md`'s canonical refs). Whatever CSS property carries "width" under the new
mechanism (a grid column's `width`/`fr` value, a `<td>`'s `width`), the same one-source-of-truth
requirement applies.

## Shared Patterns

### Escaping stays at the leaf (apply to any new box/cell builder)
**Source:** `MMM-SPCOutlook.js:541-542` comment, `:547-550` (`detailFieldBox`)
**Apply to:** any function this gap closure introduces that wraps already-resolved content in a
new structural element (a grid cell, a `<td>`) — it must never call `escapeHtml` itself; the
caller escapes before handing content in, exactly as `detailFieldBox` does today. Violating this
is exactly the class of defect `detailColoredSpan`/`detailColoredWrapper`'s split exists to
prevent (see `19-PATTERNS.md`'s "Escaping / color / truncation" shared pattern, still binding).

### One derived quantity, never restated (`Math.max(DIMENSION_FIELD_WIDTH, dimensionField.length)`)
**Source:** `MMM-SPCOutlook.js:751-757` comment + `:757`
**Apply to:** whatever replaces the winner-box/co-winner-blank-box/`also:`-spacer derivation.
This is a locked, multi-iteration-hardened invariant (WR-02 iteration 4, BL-02) — the gap-closure
mechanism must keep exactly one place that computes this width and three consumers that read it,
never three independent computations that can drift.

### Width value sanitisation before it reaches a style attribute
**Source:** `MMM-SPCOutlook.js:543-546` comment, `:548-549`
(`String(Math.max(0, Math.trunc(Number(widthCh)) || 0))`)
**Apply to:** any new numeric value (a computed column width, a grid-template-columns track size)
that is influenced, even indirectly, by payload data (an unmapped dimension name's length) before
reaching an inline `style` attribute — mirrors `validHazardColor`'s posture for color. Only
digits (or a small closed vocabulary of CSS track units) may ever reach the attribute.

### Mutation-proof every re-expressed scenario individually (Phase 15 D-10, blocking, repeated
verbatim from `19-PATTERNS.md` because it applies again here)
**Apply to:** each of the three `uat05-*` re-expressions. A scenario green under its own mutation
is a fixture defect, not a pass — this is literally the failure class that let the original
UAT-5 defect ship past 123 (now 190) green scenarios.
