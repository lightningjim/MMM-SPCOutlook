# Phase 19.1 Plan 06: Grid-Track Column Mechanism and Available-Space-First Region Cap Summary

**Replaced the disproven `32.4rem` content-needs-only region cap with `REGION_CAP_REM = 22.5` derived from the measured 1080x1920 rotated-panel geometry, and replaced the character-advance (`ch`/monospace) detail-row column mechanism with CSS Grid (`display:inline-grid` rows of `minmax(0,Nfr)` tracks) so the width-overflow defect class is now structurally impossible rather than merely bounded — landed entirely inside the existing `<span style="...">`/`<br/>` tag shapes, so `INERT_MARKUP_ALLOWLIST` needed no new entry.**

## Performance

- **Duration:** ~55 min
- **Tasks:** 3/3 completed
- **Files modified:** 2 (`MMM-SPCOutlook.js`, `scripts/probe-payload-resilience.js`)

## Accomplishments

- `REGION_CAP_REM = 22.5` (450px at the host's 20px root) replaces `32.4rem` (648px), with the derivation comment stating the measured geometry, the budget arithmetic, and the `rem` conversion in that order, citing `19.1-LIVE-CHECK.md`.
- The detail-row column mechanism is now CSS Grid: `detailTrack(fr)` emits a sanitised `minmax(0,Nfr)` track; `detailRowOpen(dimensionTrackFr)` opens an `inline-grid` row with three identically-declared tracks; `detailFieldCell(innerHtml)` replaces `detailFieldBox` with no width argument; `detailColoredWrapper` now carries colour via `display:contents` instead of `white-space:pre-wrap;font-family:monospace`.
- `detailColoredSpan` (dead code, zero call sites) deleted; every remaining comment reference to it reworded rather than left dangling.
- The one derived quantity (`Math.max(DIMENSION_FIELD_WIDTH, dimensionField.length)`, renamed `dimensionTrackFr`) still feeds the winner row, the BL-02 blank co-winner cell, and the `also:` row's own dimension track — computed exactly once, never restated.
- `alsoIndent`/`alsoLabelFieldWidth` (the arithmetic that kept the em dash on-column under the retired box mechanism) are deleted; the shared grid track now guarantees column alignment structurally.
- The last literal space-run indent in the detail markup (the probabilistic sub-line's five-space run) is retired in favor of `DETAIL_SUBLINE_INDENT_REM` padding.
- `INERT_MARKUP_ALLOWLIST` (`scripts/probe-lib/module-stubs.js`) is byte-identical (`git diff --exit-code` exits 0) and the probe suite reports zero `assertInertMarkup` violations — confirming the mechanism_decision's premise that CSS Grid expressed as style-attribute values needs no new tag shape.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Two probe scenarios' `.includes("%")` check false-positived on the grid row's own CSS**

- **Found during:** Task 3, running the probe suite after rewiring the call sites.
- **Issue:** `rpt03-detail-shape-day-3-renders-one-inline-cig-and-no-icon-line` and `rpt03-detail-shape-extended-days-render-plain-label-only` assert "no percentage" for shapes that carry no probabilistic badge. The plan's own mandated row markup (`detailRowOpen`'s `width:100%`, action (b)) introduces a literal `%` character into every rendered row, which a bare substring check cannot distinguish from a real probRisk percentage segment.
- **Fix:** Verified the only two `%`-producing code paths in the file are the CSS width declarations (`width:100%;`/`max-width:100%;`, never followed by a space) and the probRisk segments (`(100 * detail.xRisk) + "% "`, always followed by a space). Narrowed both assertions to `rendered.includes("% ")`, restoring their original intent without weakening them.
- **Files modified:** `scripts/probe-payload-resilience.js`.
- **Verification:** Both scenarios pass; full suite re-run confirms no other scenario regressed as a result.
- **Committed in:** `4e5224a` (Task 3 commit).
