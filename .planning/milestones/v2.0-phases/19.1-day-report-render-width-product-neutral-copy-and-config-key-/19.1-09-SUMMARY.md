# Plan 19.1-09 Summary

**Proved on the deployed Raspberry Pi that the detail-mode day report no longer overlaps the centre
column, closing the blocking limb-1 gap that Phase 19.1 had failed twice to close.** No code changed:
the cap derived available-space-first by plan 19.1-06 was correct as derived.

## What happened

This plan was resumed from a pause. Its first pass (2026-09-10, commit `c2d17f1`) stopped at Task 1
with a named blocker: the live mirror's `config.js` read `dayReportDetail: false`, so the every-day
detail-row width observation could not be made, and the plan forbids flipping that value without a
fresh operator authorisation. This session obtained one.

**Task 1 — both preconditions PASS.** Precondition 1 was re-confirmed rather than re-taken: the
deployed `MMM-SPCOutlook.js` SHA256 (`e951fb51…`) is byte-identical to local HEAD `c2d17f1`, which is
two docs-only commits ahead of the `2b54dc3` recorded at deploy time — the matching digest is itself
the proof those commits touched no source. Five presence markers non-zero; both ABSENCE markers
(`32.4rem`, `DejaVu Sans Mono`) exactly `0`, which is the stronger check: it proves the retired
mechanism is gone from the *deployed* file, not merely from the local one. Precondition 2 was cleared
by the authorised flip, applied line-scoped with a `-19.1gap` backup, verified by a one-line `diff`,
and then positively re-read and node-parsed rather than assumed.

**Task 2 — 9 PASS, 1 NOT OBSERVABLE, 0 FAIL.** The operator's disposition was `"Approved for all"`.
Item 1, the blocking truth, was stated directly against the 19-UAT test 5 baseline screenshot: the
block no longer extends into the centre column. Item 3 (no wrapping anywhere) is the complementary
evidence that the cap is not too *tight* either — the plan's own rule treats wrapping on ordinary rows
as the signal to raise the cap toward the 24rem ceiling, and no such evidence exists.

**Task 3 — documents reconciled, zero code diff.** The `approved` disposition selected part (a)'s
no-change branch. `19.1-UI-SPEC.md`'s pending marker was replaced with the live outcome and its
typeface-reversal item recorded as accepted; `19-PARITY-CHECKLIST.md` gained a Gap-Closure Addendum
naming the four current `uat05-*` scenarios.

## Deviations from the plan

1. **Log path wrong in the plan's `<interfaces>` block.** It records `~/MagicMirror/mm-out.log`, which
   does not exist on the Pi. The real path is `~/.pm2/logs/mm-out.log` (from `pm2 describe mm`). The
   first live check evidently read the right file while recording the wrong path in prose. Corrected
   in `19.1-LIVE-CHECK-2.md` for future runs; the plan file is left as written, since plans are
   historical records.
2. **One targeted follow-up question beyond the plan's script.** Items 5 and 6 were in apparent
   tension — an `also:` row requires two hazards on a day, and item 5 reported only one hazard
   overall. Banking item 6 as a clean PASS on that basis would have repeated the exact defect the plan
   exists to prevent, on the one item the plan singled out for deliberate re-check. The follow-up
   established that an `also:` row *is* on screen, separating the two items: a demoted second hazard
   exists; a co-equal pair does not.
3. **Two acceptance criteria reconciled against their literal wording.** The criterion requires
   `grep -c 'PENDING LIVE CONFIRMATION'` to return `0`, which conflicts with quoting the marker inside
   history-preserving passages; the historical state is now described rather than the literal string
   restated, satisfying both. The frontmatter key was also corrected to the plan's literal
   `phase_19_1_gap_probe_result`.
4. **No re-deploy.** Task 1 step 4 describes a deploy; the code was already deployed and digest-proven
   identical from the paused pass, so re-running `rsync` would have been ceremony. The verification
   that matters — the digest and marker comparison — was performed in full.
