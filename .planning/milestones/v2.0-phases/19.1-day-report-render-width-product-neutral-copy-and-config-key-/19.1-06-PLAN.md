<mechanism_decision>
## The chosen mechanism, and why it is the operator's remedy without the allowlist blast radius

`19.1-VERIFICATION.md` records the operator's chosen remedy: "REPLACE character-advance alignment
with layout-based alignment (CSS grid or a fixed-layout table)." Both named options were assumed to
require new tag shapes (`<div>`, `<table>`/`<tr>`/`<td>`), which is why `19.1-RESEARCH.md`
(Anti-Patterns, Pitfall 3) and `19.1-UI-SPEC.md` (Detail line — Harness compatibility) warn against
them: a new tag shape forces a new `INERT_MARKUP_ALLOWLIST` entry that every one of the ~190 existing
frontend scenarios then re-exercises.

**That assumption is false for CSS grid.** `display:inline-grid` is a CSS *property value*, not a tag.
A `<span style="display:inline-grid;grid-template-columns:...">` with `<span>` children is CSS Grid
layout expressed entirely inside the tag shapes the allowlist already accepts. The colour carrier
keeps its role by switching to `display:contents`, which removes its own box while still passing its
inherited `color` down, so its two child cells become grid items of the row.

**Decision:** CSS Grid via `display:inline-grid` on the existing row `<span>`. This delivers exactly
the operator's chosen remedy (layout-based alignment; no monospace stream; no `ch` unit) while
`INERT_MARKUP_ALLOWLIST` stays byte-identical. This is a deliberate, recorded choice — not a silent
side effect — and it is pinned as an explicit acceptance criterion in this plan (Task 3) and
re-asserted in the probe suite by plan `19.1-07`. Neither `<div>`, `<table>`, `<tr>`, `<td>`, nor any
other new tag shape is introduced anywhere.

**Why grid `fr` tracks and not `rem`/`px` tracks.** A track expressed in absolute units is another
content-needs-first number: it is an estimate of how wide 23 characters of Roboto Condensed happen to
be, and it can exceed the budget the same way `32.4rem` did. `fr` tracks inside a `width:100%` row
distribute *the budget that already exists*. The row can never be wider than its container, and the
container is capped at 22.5rem. **The defect class becomes structurally impossible rather than merely
bounded** — that is the correct answer to "derive from measured available space first."

**Rejected here, restated so nobody re-opens them:** shrinking detail-row type to ~0.7rem/14px
(rejected by the operator on readability at mirror viewing distance) and cutting
`DETAIL_LABEL_FIELD_WIDTH` from 23 toward ~15 (rejected by the operator because it truncates
information off the screen). Neither is planned; neither is an option in this plan's Task 3.
</mechanism_decision>
