# Phase 19 — UI Design Contract

> Visual and interaction contract for `getDom()` — the unified day report. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.

**Read this first:** this is not a web-app UI phase. There is no build step, no component
library, no input device, and (today) no CSS file — every color is an inline
`style="color:#RRGGBB"` string inside `wrapper.innerHTML +=` concatenation, on a wall-mounted
display with no keyboard/pointer/touch. Several template sections below are adapted or marked
not-applicable for that reason; each says so explicitly rather than being silently dropped or
filled with web defaults.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — vanilla JS, no build step, no framework, no component library. shadcn's initialization gate does not apply (not a React/Next.js/Vite project). |

| Component library | none |

See "Detail-Mode Column Alignment" below. |

## Layout Grammar (replaces "Spacing Scale" — px does not apply to a flowing text render)

This module has no box model, no cards, no CSS-driven margins. "Spacing" here means leading
space characters and `<br/>` line breaks inside a text stream. The 8-point px scale from the
template is not meaningful; the actual contract is character counts and line breaks, given
below precisely so two engineers implementing this independently produce byte-identical
whitespace.

### Compact line (default, `dayReportDetail: false`)

```
Day 3 (Thu)  Convective Enhanced · Flash Flood Slight · Heat Major
Day 4 (Fri)  Convective Slight · Flash Flood Marginal
```

- `Day {N} ({Weekday})` then **exactly two literal spaces**, then the hazard list. No colon
  (this deviates from the legacy `dowToText(dow) + " (Day 1): "` colon pattern — the two-space
  gap is the user's own verbatim target shape, locked in CONTEXT.md's `<specifics>`; do not
  reintroduce the colon).
- Hazard segments are joined by ` · ` — one space, U+00B7 MIDDLE DOT, one space. The dot itself
  carries **no inline color** (renders in the host's inherited default text color) so it never
  visually fuses with either adjacent hazard's color.
- Each hazard segment (`<Dimension> <Label>`, e.g. `Convective Enhanced`) is wrapped in one
  `<span style="color:#{validHazardColor(hazard.color)}">` — the dimension name and the label
  share one color, one span. Do not color the dimension name and label separately; they are one
  visual unit (D-02).
- The `Day N (Weekday)` label itself carries no inline color — same neutral/host-default text
  as the separators. **Rule for this whole phase: color is reserved for hazard content only.**
  Day labels, separators, source attribution, `also:`, and band headings all render in the
  host's inherited default text color. This is the one new structural color rule this spec
  adds — see "Color" below.
- No line-length cap, no `white-space: nowrap`, no ellipsis-by-CSS. If a compact line is wider
  than the module's region, let it wrap naturally (default browser text reflow). The only
  truncation point remains the existing per-label `truncateHazardLabel` / `HAZARDS_LABEL_MAX_CHARS
  = 60` — do not add a second, line-level truncation rule (see "Degradation & Truncation" below).
- **Row budget is a proven structural ceiling, not a policy call:** 8 dot-separated segments
  maximum, on grid days 3–5 only (one segment per `hazardTaxonomy.js` dimension, at most one
  survivor per dimension per day — RESEARCH.md's "Worst-Case Survivor Count" table). Days 1–2
  cap at 5, days 6–14 cap at 7. **No cut is needed.** If a narrower cosmetic cut is ever wanted
  for a specific small display, it must cut at a fixed `DIMENSION_ORDER` position (e.g. keep
  the first 6, note the rest are in detail mode) — never a width-measured or severity-ranked
  cut, per 18 D-15's deterministic-order requirement.
- Vertical rhythm: **no blank line between compact day rows.** One `<br/>` per day, immediately
  followed by the next day's line — matches today's density (a compact-mode mirror should read
  exactly as dense as the current one).

### Proximity-only compact exception (D-08)

```
Day 2 (Wed)  0.3 (near Marginal)
```

This is a named, explicit exception to the `<Dimension> <Label>` rule above — it is the
**only** compact segment in this entire spec that does not carry a dimension name. Do not
"fix" it into `<Dimension> <Label>` shape by prefixing a dimension name; the omission is the
user's own verbatim target shape (CONTEXT.md `<specifics>`), not an oversight to correct.

- **Format:** whatever `proximityBadge(prox, "outside")` returns, verbatim. Reuse that function
  unmodified; do not re-derive, reformat, or trim the string. **Note its return value carries a
  leading space:** `MMM-SPCOutlook.js:236` is
  `return " " + weight.toFixed(1) + " (near " + tierLabel + ")";`, so the literal return for the
  mockup row is `" 0.3 (near Marginal)"` — leading space included. The tier label itself comes
  from the CIG-vs-categorical split at `:233-235` (`cigLabelFromTierString(prox.nextTier)` when
  `nextTier` starts with `"CIG"`, otherwise `nextTier` raw), and the badge only renders when
  `hasRenderableProximity()` passes — including its `PROX_MIN_WEIGHT` (0.1) floor.
- **Indentation:** `Day N (Weekday)` then **one** literal space, then the verbatim function
  return. Because that return embeds its own leading space, the rendered gap is exactly two
  spaces — identical to every other compact line, and byte-identical to the mockup above. Do
  **not** write two literal spaces here: concatenating two literal spaces with the function's
  embedded one yields three, breaking both the mockup and the compact-line grid. This is the
  same treatment the inside-mode badge receives under D-07 below (label + verbatim return, no
  added literal space) — both call sites append `proximityBadge()`'s output directly and let its
  embedded leading space supply the separator. The badge occupies the same position a normal
  `<Dimension> <Label>` segment would; no extra offset, no dimension-field indent.
- **Color:** uncolored — no inline `style="color:..."` span at all, host's inherited default
  text color, same treatment as `Day N (Weekday)`/separators/`also:`. This is a second, narrow
  carve-out from "hazard content is colored" (alongside the day label itself): a
  proximity-to-a-tier reading describes closeness to a hazard the location is **not** currently
  in, so it reads as a structural distance note, not payload hazard data. It also matches the
  shipped `proximityBadge()` at `:230`, which returns a bare, uncolored string in `"outside"`
  mode today — preserving that exactly is what the PROXUI-01..05 RPT-06 parity gate requires;
  there is no reason for this phase to introduce a new color decision the legacy renderer never
  made.
- **Scope:** applies only when D-08's own trigger fires — a day with no surviving hazard
  (D-03 would otherwise skip the day entirely) but with `proximityWeighting: true` and
  `hasRenderableProximity()` true for the day's outside-mode categorical proximity. On a day
  that already has a real hazard survivor, the day renders its normal `<Dimension> <Label>`
  segments per D-01–D-03 only; this badge never appends onto or mixes into that dot-separated
  list — D-08 exists to give a would-be-empty day content, not to add a ninth kind of segment
  to an already-populated day.

### Detail line (per-day, `dayReportDetail: true` or auto-expand)

```
Day 1 (Tue)  Convective Enhanced · Heat Major
  Convective   Enhanced → Moderate 0.4   — SPC
     🌀② 10%  ⬚① 30%  💨 15%
  Heat         Major                     — HeatRisk
                 also: Hazardous Heat    — WPC Hazards
```

Column contract (character offsets, measured from the left margin of the day block, indent
level 0 = the compact header line above):

| Element | Indent | Notes |
|---|---|---|
| Compact line (header, D-06) | 0 | Identical to the compact render above — restated verbatim, not summarized or abbreviated. This IS the header; do not build a second, different header string. |
| Dimension sub-row | 2 spaces | One sub-row per dimension present on the day, in `DIMENSION_ORDER` (18 D-15), resolved entry (`suppressedBy === null`) only |
| — dimension name field | cols 3–15 (13 chars, left-aligned, space-padded) | Widest known dimension name is "Flash Flood"/"Heavy Precip" (11–12 chars); 13 gives at least one trailing space against every current taxonomy entry. If `hazardTaxonomy.js` ever adds a longer dimension name, recompute this field width as `longest dimension name + 1`, not a hardcoded 13. |
| — label field | cols 16–38 (23 chars, left-aligned, space-padded) before the source-attribution gap (see below) | Colored per the same rule as compact: dimension name + label text share one `<span style="color:#...">` |
| — source attribution | `   — {SourceDisplayName}` (3 spaces, em dash, 1 space, then the source's display name, e.g. `SPC`, `HeatRisk`, `WPC Hazards`), em dash lands at col 42 | **Uncolored** (structural, not hazard data) — this is RPT-03's whole reason to exist: attribution is exclusive to detail mode, so it must read as metadata, not as another hazard |
| Probabilistic sub-line (D-07, days 1–2 convective only) | 5 spaces (2 base + 3) | Beneath the convective sub-row only. NOT column-aligned to the label field — it's a subordinate wrapped line under the whole row, not a value in a column. Icon + CIG glyph + per-type proximity badge + percentage, space-separated, in `torRisk, hailRisk, windRisk` order (matches legacy) |
| `also:` competing-claim line (D-05) | 17 spaces (2 + 13-char dimension field + 2 more) | One per suppressed entry on that dimension, same order the payload provides (18 D-03 — never re-sorted). Format: `also: {Label}` then the same source-attribution gap/format as the winner's row. The competing label text IS colored in its own payload color (all entries render, 18 D-13 — a competitor is not visually punished by being uncolored); only the `also:` word and the source attribution stay neutral. |

**Label field width, derived exactly from the CONTEXT.md mockup:** the em dash of every
source-attribution string lands at the same column (42) regardless of row — verified
byte-for-byte against `Enhanced → Moderate 0.4` (23 chars, fills the field exactly) and `Major`
(5 chars, padded with 18 trailing spaces to fill the same field) in the mockup. 42 (em dash
col) − 3 (attribution gap) = col 39 is the first column after the label field, so the field
itself is cols 16–38 inclusive = **23 characters**, left-aligned, space-padded with trailing
spaces when the content is shorter. This is the exact number; do not round or approximate it
elsewhere in this document (see "Degradation & Truncation" below, which previously referred to
it as "~24-char" — corrected to 23 there too, so every reference to this field agrees).

**Inside-mode proximity badge (D-07, detail only).** The ` → {nextTier} {weight}` suffix
appended to a convective sub-row's label (e.g. `Enhanced → Moderate 0.4`) is part of that row's
label-field content, not a separate structural element — it shares the same
`<span style="color:#...">` as the label text ahead of it (one span, same rule as the compact
line's `<Dimension> <Label>` unit), because it describes where the day's own active hazard is
trending, not a near-miss to a tier the location isn't in. This is the **opposite** color
treatment from the D-08 compact exception above (intentionally uncolored, since it describes a
tier the location is near but not in) — inside mode colors, outside mode does not. Produced by
the shipped `proximityBadge(prox, "inside")` at `MMM-SPCOutlook.js:230`; reuse verbatim, same as
the outside-mode call site.

**Detail-Mode Column Alignment.** Roboto Condensed is proportional; space-padding a proportional
font does not produce visually aligned columns. To make the table above actually line up on
screen, apply an inline `style="font-family:'DejaVu Sans Mono','Liberation Mono',monospace;"` to
whatever element wraps each detail sub-row block (or, if the chosen render mechanism has no
such wrapping element — e.g. pure string concatenation with no enclosing `<div>` per day —
repeat the font-family declaration on each generated sub-row's own inline `style` attribute,
consistent with the existing per-span inline-styling convention). **This does not require a new
CSS file or `getStyles()` entry** — it is one more inline style, same pattern the module already
uses for color, so it does not force the open "should this module ship a stylesheet" decision
either way. DejaVu Sans Mono ships by default on Raspberry Pi OS.
Compact-line text and everything outside detail sub-rows keeps the host's inherited proportional
font — only the aligned sub-row block switches font-family.

**Do not use font-size to establish hierarchy.** Viewing distance is meters, not centimeters
(project constraint) — shrinking the probabilistic sub-line or the `also:` line to look
"secondary" makes it illegible from across a room, the opposite of the goal. Hierarchy comes
from indentation depth and the color/neutral split above, never from a smaller font size. No
new font-size, font-weight, or line-height override is introduced anywhere in this phase;
everything inherits the host's size/weight/line-height except the one font-family swap above.

**Vertical rhythm in detail mode:** one blank line (`<br/><br/>` effectively — one extra break)
between each expanded day's block and the next day's block. Without it, a 3–5 line expanded
block runs directly into the next day's header with no boundary, which reads as one confused
block on a mirror with no card/border affordance available. Compact-only days adjacent to an
expanded day still get the same trailing blank line, so the rhythm doesn't visually announce
"this day was special" — it stays uniform across the whole list, avoiding an unintended
indicator that a day auto-expanded (see "No Chrome for Auto-Expand" below).

### No Chrome for Auto-Expand (D-04)

An auto-expanded day (per-dimension significance floor cleared) and a day expanded only because
`dayReportDetail: true` is set globally render **identically** — same header, same sub-rows,
same spacing. Do not add a marker, icon, or color hint distinguishing "this expanded on its
own" from "this expanded because you turned detail mode on." The mechanism is invisible by
design (D-04's own framing: surface serious days without the user reconfiguring anything — the
surfacing IS the feature; announcing the mechanism would be a second feature nobody asked for).

### The Band (RPT-04 — below all day blocks)

```
[day blocks, as above]

[SPC MD lines, existing format, uncolored-attribution / blue content, unchanged]
[WPC MPD lines, existing format, unchanged]
Extended Hazards:
[window-spanning Hazards Outlook lines, existing format, unchanged]
```

- **One blank line** separates the last day block from the band's first line — the same
  vertical-rhythm rule as between two day blocks, so the band reads as "one more block," not a
  visually disconnected footer.
- Internal ordering and wording are **unchanged from today**, only relocated: advisories first
  (SPC MD then WPC MPD, existing concatenation order, existing `{label} [— {hazardType}] in
  effect.` wording, existing `#0059E0` blue, existing escaping) — then the Hazards Outlook
  window band (existing span-start order, existing `"Extended Hazards:"` heading written once
  before the first renderable entry, existing `(D3)` / `(D3–7)` offset formatting). **Do not
  invent a unifying heading for the combined band** — the advisories' existing blue identifies
  them, and the window band's existing heading identifies itself; adding a third label ("Below:"
  or similar) would be new copy nobody asked for.
- **One offset form is new this phase (19-REVIEW BL-03):** a window that STARTED before today
  and has not yet ended (`offsetStart < 0 <= offsetEnd`) renders as `through {Weekday} (→D{end})`
  rather than `{Weekday}–{Weekday} (D{start}–{end})`. The `D<n>` segment is 1-based like every
  `Day N` block above it, so a raw negative start rendered `(D0–4)` under a grid whose first row
  is Day 1 — the band contradicting the grid directly above it. The elapsed portion is not
  forecastable content and is therefore not advertised at all: the range is left open at the low
  end rather than clamped to a start day the feature did not begin on (clamping would pair a past
  start weekday with a present-day offset, the same disagreement one level down). Every
  non-negative offset keeps the existing `(D3)` / `(D3–7)` formatting exactly.
- **Record this relocation on the RPT-06 checklist as verified-intentional**, not investigated
  as a regression (RESEARCH.md Pitfall 3) — today's advisories render above the day rows; RPT-04
  requires below.
- IN-01's dedupe-key collision (a `|`-containing remote label silently dropping a band entry) is
  a backend key-construction defect, not a rendering decision — this spec does not change band
  rendering to work around it; the fix belongs in `node_helper.js:939`, not `getDom()`.

### Global Stale Badge (D-09 — position now decided)

`⚠ Stale — {age}` renders **first, at the very top of all content**, before any day block and
before the band — unchanged content, unchanged CR-01 guard (a stale payload with no renderable
risk must still show real content beneath the badge, never a bare `⚠`). Placing it at the very
top (rather than between day blocks and the band, or anywhere else) keeps it reading as a
document-level status line rather than attached to any specific day or the band, which matches
its actual scope (18 D-04's per-source staleness stays unrendered — out of v2.0 scope per
PROJECT.md; only this one global marker exists).

## Interaction States — Not Applicable (documented, not omitted)

There is no keyboard, pointer, or touch input on this display. Do not specify hover, focus,
active, or disabled states; nothing in this render is clickable, hoverable, or focusable. The
only "interaction" a user has with this module is editing `config.js` (`dayReportDetail`,
`proximityWeighting`, per-product toggles) and restarting — a build-time/config-time decision,
not a runtime UI interaction. Accessibility framing follows the same rule: standard contrast
reasoning applies to legibility (see Color above — NOAA palette colors are validated but not
otherwise adjusted for contrast, since they are data, not this module's to recolor), but
keyboard navigation, focus order, and ARIA roles do not apply — there is no user agent
interacting with this display.

CTA and destructive-confirmation rows from the template do not apply — there is no button, no

working logic — one new upstream branch, zero changes to the CR-01 guard itself — because
Pitfall 9's whole warning is that a rewrite silently drops something that already works.

## Detail-Mode Density (Priority 4 — the `detail` sub-object's three shapes)

RESEARCH.md's most load-bearing finding for this section: a convective entry's `detail`
sub-object is **not one shape**. The sub-row and sub-line rendering must branch on which fields
are present — a renderer built only against the days-1–2 shape (the only shape CONTEXT.md's own
D-07 example shows) will misrender or throw on days 3 and 4–8.

| Grid days | `detail` shape | Sub-row label field shows | Probabilistic sub-line? |
|---|---|---|---|
| 1–2 | `{probRisk, torRisk, torCig, hailRisk, hailCig, windRisk, windCig}` | `{Label} → {nextTier} {weight}` (proximity, detail-only per D-07) or plain `{Label}` if no renderable proximity | **Yes** — full `🌀{cig} {pct}% ⬚{cig} {pct}% 💨{cig} {pct}%` line, 5-space indent, only per-type when that type's own risk `> 0` (matches legacy per-type gating) |
| 3 | `{probRisk, cig}` — one combined CIG, no per-type breakdown | `{Label} {cigLabel(cig)}` — the CIG glyph (①②③) appended directly into the label field, matching today's day-3 inline treatment | **No** — there is nothing to break into a per-type line; do not fabricate one |
| 4–8 (extended only) | `{probRisk, sign}` | `{Label}` — plain, no glyph, no percentage | **No.** `sign` has never been rendered by any shipped `getDom()` (Open Question 3) — do not add new UI for it. This is a deliberate no-op, not an oversight; if a future phase wants to surface `sign`, that is a new feature decision, not something this parity-gated phase should introduce. |
| 9–14 (convective winner is `wpc-hazards`, not `spc-convective`) | no `detail` object at all | `{Label}` — plain, exactly like any other `wpc-hazards`-sourced dimension | **No** — `wpc-hazards` carries no severity/probability breakdown for any dimension |

**Accepting the height cost honestly:** at the proven 8-dimension ceiling (grid days 3–5), a
fully expanded day can legitimately run 10–14 physical lines (8 dimension sub-rows, up to one
probabilistic sub-line, plus any `also:` lines for suppressed competitors on contested
dimensions). Do not compress this — all entries rendering is D-05's explicit requirement, and
"relocation is acceptable, silent loss is not" is the standing rule for any layout question this
document doesn't cover. MagicMirror regions grow/scroll to fit their content; this spec adds no
artificial height cap. Each sub-row and `also:` line should stay exactly one physical line
(the probabilistic sub-line is the one place a wrap is expected, and even that stays one line at
normal region widths) — do not let a single hazard's rendering spill across multiple visual
lines beyond what's specified above.

## Degradation & Truncation (Priority 5)

- **Unmapped remote labels render verbatim** (18 D-07) and are truncated at exactly
  `HAZARDS_LABEL_MAX_CHARS = 60` source characters, **before** escaping — reuse
  `truncateHazardLabel` verbatim; do not write a second truncation rule for the unified
  renderer's own call sites (WR-06's "a fix applied to one twin and not the other" is this
  codebase's recurring defect, and the unified renderer collapses what were two hazard call
  sites into one — keep it that way, one shared helper, one call site class).
- **Compact line:** no line-level cap exists or is needed (the 8-segment ceiling is structural,
  proven, not policy — see Layout Grammar). A single 60-character unmapped label inside one
  segment is the realistic worst case; let the whole compact line wrap naturally if it doesn't
  fit the region width. Do not clip with CSS `overflow`/ellipsis at the line level — that would
  silently hide a hazard, which is the one thing this whole phase must never do.
  `truncateHazardLabel`'s existing 60-char/`…` cap remains the only truncation point, applied
  per-label, not per-line.
- **Detail-mode column alignment degrades gracefully, not catastrophically:** a label wider
  than its field's assumed width (Layout Grammar's 13-char dimension field / 23-char label
  field are sized for the known taxonomy vocabulary, not a 60-char unmapped worst case) breaks
  alignment for that one row only — every other row computes its own padding independently, so
  a long label never cascades misalignment into subsequent rows. This is an accepted, rare-case
  cosmetic degradation, not a defect to engineer around with more truncation.
