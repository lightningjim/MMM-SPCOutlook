  <action>
Extend the EXISTING `memberTimings` object rather than building a parallel timing structure — D-17
says the per-product breakdown extends what PERF-01 already built.

In `getSpcOutlook`, capture `this._nowMs()` immediately before the SPC convective day-1 block begins
and again immediately after the fire-weather inline block ends, and record the elapsed value into
`memberTimings` under two keys. Because the SPC convective and fire-weather code is interleaved
rather than cleanly separated, measure the two spans that actually exist: record
`spc-convective` and `spc-fire` separately if their code is contiguous, and if it is not, record a
single `spc-inline` entry covering the whole inline span with a comment stating that the two products
share one serial code path and cannot be timed apart without restructuring, which is out of scope for
this phase. Decide from the source, not from this plan, and state which shape you chose and why in
the SUMMARY.

Comment that these entries are NOT part of the `Promise.allSettled` batch: the inline SPC/fire chain
runs serially before the batch, so its time ADDS to the poll's wall time rather than overlapping with
it. Without that note a reader will wrongly assume the sum of `memberTimings` is the poll duration.

Add a `slowest` derivation over the completed `memberTimings` object: the key with the maximum value.
D-17 asks for a breakdown "naming the slowest fetch", so name it in the log line rather than leaving
it to be read out of a JSON blob. Return the timing data out of `getSpcOutlook` — attach it to a
helper-global (`this._lastPollTimings`) set immediately before the return, rather than adding a key
to the payload. A timing field in the payload would cross the socket, would change on every poll, and
would defeat PERF-02's byte-identity intent for cache comparison; the socket handler is in the same
process and can read the helper-global directly. Comment that reasoning at the assignment.

In `socketNotificationReceived`, capture `const t0 = this._nowMs();` immediately after the
`notification === "GET_SPC_DATA"` check and BEFORE the `_inFlight` guard, and compute the elapsed
interval immediately before the `sendSocketNotification("SPC_DATA_RESULT", ...)` call. Do not add a
new try/finally — the existing `_inFlight` try/finally already brackets exactly this span, and the
early `return` on an in-flight poll correctly measures nothing because no result is emitted on that
path.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Frontend `GET_SPC_DATA` request -> backend timing bracket | The timed span is driven by a socket message the frontend controls the rate of. |
| Timing values -> log output | Log lines are written to the MagicMirror process log, which an operator reads. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-18-17 | Denial of Service | log volume from timing instrumentation | mitigate | The summary block is guarded by `this._loggedColdStartTiming` / `_loggedFirstPayloadMs` and fires once per process, roughly four lines (D-18's accepted cost). The existing per-poll batch line is unchanged. No timing log is added inside any per-feature or per-layer loop. |
| T-18-18 | Information Disclosure | timing figures crossing the socket in the payload | mitigate | Timings are held on `this._lastPollTimings`, a helper-global read in-process by the socket handler, and are never added to the emitted payload. This also preserves PERF-02's byte-identity intent for cache comparison, which a per-poll varying field would defeat. |
| T-18-19 | Repudiation | a wall-clock figure attributed to a render the user never saw | mitigate | The frontend log fires only after every existing acceptance guard (sequence, epoch, lat/lon), so a rejected payload cannot consume the once-per-process guard or produce a misleading figure. |
| T-18-20 | Tampering | a frontend driving repeated `GET_SPC_DATA` to skew timings | accept | The existing `_inFlight` guard (CR-03) already drops overlapping polls, and the summary block only fires on a poll that actually emitted a result. Single-instance, local-socket deployment; no adversarial frontend exists. |
| T-18-SC | Tampering | npm/pip/cargo installs | accept | No package-manager install tasks in this phase; RESEARCH.md confirms zero new dependencies. |
</threat_model>
