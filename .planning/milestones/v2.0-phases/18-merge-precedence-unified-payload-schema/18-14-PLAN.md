<objective>
Close the CR-04 half of `18-VERIFICATION.md`'s gap 1: `_spcGridAnchor` validates that `expireMs` is
finite but never that the window it describes is still in force. SPC does not replace
`day1otlk_cat.lyr.geojson` instantaneously at 12Z — this phase's own research comment records a live
`VALID 13:00Z / EXPIRE 12:00Z-next-day / ISSUE 12:54Z` observation — and this module additionally
serves cached bodies for up to `2 * _updateInterval`. During that window the served `EXPIRE_ISO` is
already in the past. `_spcGridAnchor` accepts it, sets `nominalStartMs` to yesterday 12Z, shifts the
entire fourteen-day grid one day early, and reports `gridAnchor: "observed"` — actively asserting
the shifted anchor is trustworthy.

Purpose: this fires only when `_validTimeOfWinner` finds a value to anchor on, which happens only
when the user is standing inside an active day-1 convective polygon. The users who get a whole-grid
day shift are therefore exactly the users for whom correct day attribution matters most. It is a
second, independent falsification of ROADMAP criterion 1 alongside the endpoint-convention defect
18-13 closes.

Output: a clock-checked observed branch in `_spcGridAnchor`, a corrected fallback log line, and one
mutation-proven probe scenario with a still-in-force control.
</objective>

<decision>
## The fix is the narrowest one that is correct: reject, do not repair

`_spcGridAnchor`'s observed branch is entered only when `Number.isFinite(expireMs)`. Add a second
conjunct — the window must not have ended — and let control fall through to the clock rule that
already exists immediately below and is already correct for this case:

`if (Number.isFinite(expireMs) && expireMs > this._nowMs()) { ... }`

Strict `>`, not `>=`: at the instant `expireMs === now` the outlook period has ended, so the anchor
it names is the previous period.

Rejected alternatives, and why:
- **Advance the anchor by a day when it looks elapsed** (`nominalStartMs + MS_PER_DAY`): this is the
  module inventing an outlook period SPC has not published, and it would still report `"observed"`
  for an anchor no source ever asserted. The clock fallback is the honest answer and already exists.
- **Widen the tolerance to `expireMs > now - someGrace`**: a grace window is a magic number with no
  live evidence behind it, and the failure mode it would buy is precisely the one this gap
  describes. There is no cost to falling back: the clock rule resolves the correct nominal start for
  every case in which `EXPIRE_ISO` is elapsed.
- **Check `day1EndMs` after the branch and re-enter**: two code paths for one decision, which is the
  WR-06 divergence shape this file already argues against.

**Second, non-optional half:** the once-per-process fallback log at `node_helper.js:4275-4278` reads
"SPC grid anchor unavailable (no VALID_ISO/EXPIRE_ISO from the day-1 categorical outlook)". After
this fix that sentence is false in exactly the new case — the fields were present and well-formed,
they had simply expired. Shipping a diagnostic that misdescribes the branch it fires on would make
the defect harder to recognise in production than it is today. The message must name both causes.
</decision>
