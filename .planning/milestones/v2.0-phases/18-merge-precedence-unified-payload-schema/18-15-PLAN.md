<objective>
Close `18-VERIFICATION.md` gap 2 (CR-02). `node_helper.js:2984` reads
`if (gridDay < 1 || gridDay > GRID_DAY_COUNT || gridDay > row.days) continue;`. `gridDay` is
numbered against the SPC 12Z grid anchor; `row.days` (7) is HeatRisk's span expressed in
product-day units anchored at UTC midnight. The two numbering systems differ by exactly one for the
whole 00Z–12Z half of every UTC day, because `_spcGridAnchor`'s clock fallback resolves
`nominalStartMs` to *yesterday* 12Z whenever `getUTCHours() < 12`. For those twelve hours the
`gridDay > row.days` term silently discards HeatRisk's seventh, outermost tile.

Purpose: the drop happens BEFORE `notes.noteReported` runs for that day, so the tile disappears from
`sources.heatrisk.reportedDays` as well as from `days[]`. `_resolveGridDayPrecedence` then takes its
"rank source absent" branch rather than "reported below floor" — a genuine Extreme-heat reading
becomes indistinguishable from HeatRisk never having covered that day, and a WPC "Hazardous Heat"
flag landing on the same day has nothing to suppress it, which is precisely the comparison MERGE-03
exists to make. Under this project's stated no-false-negative rule a heat reading that silently
vanishes for half of every day is the most severe defect class defined.

This is a DIFFERENT defect from the already-filed Phase 17 legacy `heatRisk.day1..day7` block issue
the operator routed to Phase 19: that one drops the NEAR day from the legacy block; this one drops
the FAR day from the unified grid. Do not conflate them and do not touch `_runHeatRiskProduct`'s
legacy day filter in this plan.

Output: the mismatched bound removed, and the suite's first sub-12Z scenario, proving all seven
tiles land under both halves of the UTC day.
</objective>

<decision>
## Drop the term; do not "convert" it

`GRID_DAY_COUNT` is already the only bound in this expression stated in grid-day units, and it
already bounds the loop safely at fourteen. `_addHazardsOutlookGridEntries` — the sibling function
on the same grid — correctly clamps to `GRID_DAY_COUNT` alone. The corrected line is:

`if (gridDay < 1 || gridDay > GRID_DAY_COUNT) continue;`

Rejected alternative: translate `row.days` into grid-day units (e.g. `row.days + anchorOffset`).
That would preserve a registry-sourced bound at the cost of introducing a second, derived
day-numbering conversion at a site whose whole defect was a day-numbering conversion error, for no
benefit — HeatRisk's span is already bounded upstream by the catalog the runner reads, and this
function iterates the tuples it is handed rather than a day range. There is nothing to bound here
that `GRID_DAY_COUNT` does not already bound.

The `WR-16` comment currently attached to that line ("the span bound is read from the registry row,
never a literal, so this product's declared span has exactly one declaration") is the justification
for the defect and must be replaced, not merely trimmed: it is true about provenance and wrong about
units, and leaving it would invite a future maintainer to restore the term.

**Review-warning rider, declared explicitly:** WR-09 records that all 37 `merge-*` scenarios pin
`now >= 12:00Z`, so the 00Z–12Z anchor branch — the branch this defect lives in — is untested by the
entire suite. That is not smuggled in as gap work; it is folded in because gap 2's own `missing:`
list already requires a sub-12Z scenario, and because the fix is otherwise unpinnable: measured at
HEAD, removing the `gridDay > row.days` term changes NOTHING in the 119-scenario suite. This plan
therefore introduces the suite's first sub-12Z clock constant and one scenario built on it. It does
not attempt WR-09's full remedy (duplicating the SPC straight-through and parity scenarios against a
morning clock as well) — that is broader than any gap requires and is left recorded, not done.
</decision>
