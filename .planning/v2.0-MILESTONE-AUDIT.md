## Integration — 0 blockers

socket → `_inFlight`-guarded `getSpcOutlook` → `Promise.allSettled` over 6 members → 5 assembly

All seven products reach the screen, each respecting its toggle end-to-end. `reporting` cannot be
true with a toggle off (`node_helper.js:3872`). Every toggle gate uses strict `=== true`/`!== true`

**RPT-01 (sole render path) was verified without relying on its probe.** Every `this.spcrisk.*`

**PERF-01 × `_inFlight` — the specifically-flagged cross-phase hazard HOLDS.** Phase 14 introduced

parallelized fetching. Three independent legs confirm the guard survived: `getSpcOutlook` has

rejection substitution so one throw cannot skip the `finally`, and
`scripts/check-concurrency-invariant.sh` self-tests its own ability to fail before asserting exact
write-site counts.

### 2. The legacy-retirement todo was factually dangerous (CORRECTED)

The pending todo listed `advisories` among blocks "that no render path reads". **It is the sole
transport for every MPD and SPC MD band entry** (`MMM-SPCOutlook.js:967`, consumed `:1498-1511`).
Executing it as written would have deleted MPD-01/02/03 and SPC MD from the display. The `rpt01`
probe's own accessor list correctly omitted `advisories` — probe and todo contradicted each other,
and the probe was right.

Corrected in place 2026-09-11, with two further corrections: `day48Risk` added to scope (a ninth
unread legacy key missing from the inventory), and a warning that retirement is **not** a pure
deletion — the RPT-04 window band is produced *inside* the legacy `hazardsOutlook` block, so
`windowEntries`/`windowBand` assembly plus `_hazardDayOffset`, `_todayUtcMs` and
`_isFullNominalWindow` must be extracted first or RPT-04 breaks.

### 3. Window band and day grid disagree about day numbers for half of every day (new, undocumented)

Phase 18 re-anchored the day grid to SPC's 12Z boundary. The window band was not — it still carries
Phase 16's raw UTC-midnight offsets. Both call `_hazardDayOffset`, with different anchors. During
the 12Z–24Z UTC half of each day — US afternoon and evening, the primary viewing window for a wall
mirror — the band's `D<n>` reads one day higher than the grid row covering the same instant.

The in-source comment claims the `+1` conversion makes the band "agree with the grid directly above
it". It does not, for half of every day: the `+1` fixed the 0-vs-1 base, but the anchor offset is a
separate, unaddressed term. MERGE-01's normalization layer is genuinely wired for the grid and
bypassed entirely for the band.

Not a blocker: no data lost, no hazard hidden, no false negative. It is a labelling inconsistency
between two adjacent regions of the same render. **It is, however, the only finding in this audit
that is recorded nowhere else in the project** — searched across `18-deferred-items.md`,
`19-CONTEXT.md`, `19-LEGACY-RETIREMENT.md` and pending todos. Phase 18 deliberately deferred band
*membership*; nothing addresses band *labelling*.

### Finding 1 — CLOSED. Phase 14 re-verified: `passed`, 13/13, `has_blocking_gaps: false`

Re-run 2026-09-11 (previous: `gaps_found`, 10/13, 2026-08-19). The verifier did not accept

breaking each guard to confirm the probe turns RED:

| M4 — drop `failed`+log on the **network-error** branch | **SURVIVED** — new finding, see below |
| M5 — ERO runner ignores `.failed` | **RED** (5) |

One correction to this audit's own reasoning: **CR-02 was fixed better than its remediation
prescribed.** The audit (and the original report) framed it as needing guards at ~11 SPC
cache-write call sites. It was instead fixed at the source — `rejectBody` returns
`data: null`, and of the 22 returns in `_fetchGeoJsonCachedInner` exactly two carry non-null
`data`, both `isValidBody`-gated, with all 22 `_geoJsonCache.set` sites inside a
`data !== null` branch. No caller can receive a rejected body at all. That is a structural
guarantee rather than a conventional one, which is why Phases 15-19 inherited the guarantee
instead of inheriting the defect.

### NEW finding — regression-coverage gap on the network-error branch (low, backlogged)

Mutation M4 survived: the probe suite cannot turn RED on a regression in
`fetchGeoJsonCached`'s **network-error** hard-failure branch. Two near-misses each land one
layer off — `throwingFetch` throws above `fetchGeoJsonCached`, and `installHttp`'s unrouted
default is a 503, which takes the *non-2xx* branch (that half IS pinned, by M3).

The code at HEAD is correct by source read, so this is coverage debt, not a live defect. It
matters more than a typical gap because it is the exact branch **CR-03** was raised about:
the dominant real-world ERO failure is a network error, and the original defect was that it
degraded *invisibly*. A silent regression here reproduces a false all-clear — the outcome
this module exists to prevent. Filed as
`.planning/todos/pending/2026-09-11-pin-fetchgeojsoncached-network-error-branch.md`.
